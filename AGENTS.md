# Log papercuts

When you encounter small friction while working—a failed tool call, confusing
setup, flaky command, stale cache, misleading error, missing helper, or
non-obvious gotcha—record it in `PAPERCUTS.md`.

Create the file if it does not exist. Append one entry in this format:

## YYYY-MM-DD HH:MM — <model>

<What you were doing> → <what got in the way>. Include a possible cause or fix
when useful.

Log papercuts proactively when they occur, but do not interrupt the main task.
Do not add duplicate entries. Papercuts are minor workflow friction, distinct
from completed-work logs and real bugs or tracked issues.

Краткие инструкции для AI, работающего с репозиторием. Пользовательская и
эксплуатационная документация проекта живёт в `README.md`; не дублировать её
здесь и не добавлять сюда журналы работы, статусы задач или датированные отчёты.

## Перед началом работы

- Читать `README.md` для понимания возможностей, конфигурации и эксплуатации.
- Считать `package.json` источником истины для команд, а
  `.dependency-cruiser.cjs` — для границ между модулями.
- Искать локальный `README.md` в затрагиваемых `composables/` и `utils/`.
- Правила по темам лежат в `.claude/rules/`: код-стайл (`vue-sfc`, `typescript`,
  `styles`, `naming`, `structure`, `vue-best-practices`, `comments` — язык и
  место комментариев) и грабли инструментов (`environment` — оболочка,
  dev-сервер, HMR, git; `testing` — vitest). Живая верификация — скилл `verify`.
- Работа с макетом — `docs/figma-sync-workflow.md`. Оттуда же жёсткое правило:
  **новый компонент в коде — компонент и в макете** (сет на 🧩 Components плюс
  инстансы на экранах), копии фреймов по бордам запрещены.

## Карта репозитория

- `src/module.ts`, `src/module-setup.ts`, `src/module-runtime-config.ts` —
  build-time настройка Nuxt-модуля; их типы — в `src/types/` (один файл на
  модуль).
- `src/runtime/modules/` — runtime-код по доменам: `builder`, `common`,
  `layouts-blocks`, `persistence`, `render`, `text-editor`, `ui`.
- `src/runtime/server/` — Nitro API, middleware и серверная инфраструктура.
- `playground/` — приложение для локальной разработки.
- `test/` — Vitest-тесты; `migrations/` — миграции БД; `scripts/` — smoke- и
  служебные проверки.

## Архитектурные правила

- Не пытаться пока поддерживать обратную совместимость, проект в стадии активной разработки и нигде не опубликован
- Использовать явные относительные импорты локального runtime-кода: его
  auto-import отключён.
- Соблюдать слоистость из `.dependency-cruiser.cjs`: `common` и `ui` — нижние
  слои, `render` не зависит от `builder`, `persistence` остаётся server-only.
- Не протаскивать builder-only зависимости в published renderer или общий
  entry-бандл. Layout-блоки описываются через definitions и registry; Vue-
  компоненты leaf-блоков подключаются лениво.
- Не хардкодить маршруты `/bricks`, `/preview`, имена роутов и пути публичных
  assets: использовать константы и helpers из `common`.
- Любой недоверенный HTML/SVG перед `v-html` или `innerHTML` пропускать через
  `common/utils/sanitize/`.
- Схему менять **в базовой миграции**, а не новым файлом: проект не опубликован,
  потребитель базы один, обратная совместимость не поддерживается, и
  forward-миграция ради пары колонок только копит файлы. Порядок: правка
  `migrations/0001_init.sql` → тот же DDL руками в живую БД → пересчёт строки
  в реестре `bricks_schema_migrations` (иначе checksum-контроль валит миграции
  как drift) → статус миграций показывает 0 pending.
- При добавлении или удалении файла в `composables/` или `utils/` обновлять
  локальный `README.md` этой папки.

## Комментарии в коде: английский язык и никаких ID задач

Полное правило — `.claude/rules/comments.md` (язык, dev-сообщения, запрет
комментариев в `<template>`/`<style>`). Автоматической проверки нет — держится
ревью. Ниже — часть про ссылки на задачи, потому что нарушают её чаще всего.

**Запрещено** ссылаться в коде, тестах, докстрингах, локальных `README.md` и
сообщениях коммитов на идентификаторы задач тех. спринтов (`BM-27`, `A-09`,
любые `<БУКВЫ>-<ЧИСЛО>`) и на файлы-планы этих спринтов
(`docs/*-followups.md`, `docs/architecture-audit.md` и подобные). Причина:
спринты временные, их логи не хранятся, и через месяц `BM-27` в комментарии —
мёртвая ссылка, по которой ничего не восстановить.

Вместо ID писать **сам факт**: что было сломано, почему сделано именно так, чем
грозит откат. Комментарий должен читаться без внешних документов:

```ts
// ❌ потолок ожидания запроса (BM-27)
// ❌ см. BM-20 в docs/brick-manifest-followups.md
// ✅ Потолок ожидания: без него зависший запрос держал бы кнопку Save
//    заблокированной бесконечно.
```

То же для `describe`/`it` в тестах — имя кейса описывает поведение, а не пункт
плана. Встретил такую ссылку в существующем коде — убрать, сохранив смысл.

- Всегда для этого агента использовать модель gpt-5.6-sol high
- Всегда указывать информацию по скиллам, которые у тебя есть, включая принятые нами правила и code-style
- Запрещать коммиты
- Перепроверять результаты за агентом на своей стороне
- **Запускать только в фоне** (`run_in_background: true`): в foreground у вызова
  лимит 2 минуты, и Codex убивают посреди чтения файлов, не дав ответа
  (проверено 28 июля 2026 — второй заход умер на 194-й секунде)
- **О завершении Codex уведомления НЕ будет — следить самому.** Задание запускает
  сабагент-форвардер, поэтому task-notification приходит о нём, а не о процессе
  Codex: в момент уведомления ревью обычно ещё идёт. Не отвечать «жду вывод» и не
  ждать, пока пнёт пользователь (проверено 28 июля 2026: два раунда подряд
  обнаружены только по его пингу).
- **Сразу после старта Codex ставить ожидание в фон** — командой
  `node .claude/scripts/wait-codex.mjs --new --timeout 240` через Bash с
  `run_in_background: true`, без самодельных циклов. Скрипт дожидается завершения
  и печатает статус, длительность, путь к логу и сам отчёт, поэтому готовность
  приходит штатным уведомлением harness. Ловит и зомби: статус `running` при
  мёртвом pid (гасить `cancel <job-id>`, перезапускать с `--fresh`).
  Потолок задавать сразу: дефолтного часа хватает не всегда — свободное ревью
  большого диффа шло 3 ч 32 мин и завершилось успешно, а ожидание вышло по
  таймауту. `CODEX_TIMEOUT` при живых фазах в пульсе значит «ждём дальше», а не
  «задание умерло».
- **`--job <id>` надёжнее `--new`.** Без отбора скрипт берёт самое свежее
  известное задание — то есть отчёт ПРОШЛОГО раунда, потому что новое ещё не
  создано; принять его за свой можно на автомате (признак — совпадающие id и
  `duration` с прошлым заданием). `--new` отсекает и прошлый раунд, и
  задание-handshake `codex:codex-rescue` (пустой промпт, ответ-приветствие на
  несколько секунд, настоящее задание идёт следующим), но у него есть вторая
  граница: если форвардер успел создать задание ДО старта скрипта, `--new` его
  не увидит вовсе. Поэтому: заметил в `status --json` id задания — перезапускать
  ожидание с `--job <id>`. Остальные флаги: `--match <строка>` (отбор по
  подстроке промпта — брать **буквальный** короткий кусок без падежей: «этап 6.2»
  против «этапа 6.2» в промпте стоило 45 минут ожидания готового отчёта),
  `--timeout <мин>`, `--tail <строк>`.
- **Апострофов в промпте не писать.** Companion собирает команду в одинарных
  кавычках, и первый же `'` её закрывает: задание умирает на старте с
  `(eval):7: parse error near ')'`, а `status --json` при этом отдаёт пустые
  `running`/`latestFinished`, то есть ожидание висело бы до таймаута. Писать
  «через PATCH», «ключ payload».
- **Промпт бывает потерян при передаче через сабагента.** Признак: задание
  отработало за секунды и вернуло приветственную справку («я могу помочь с этим
  репозиторием»), в записи задания `request.prompt` пустой. Это не отчёт —
  перезапускать. Надёжный обход для больших промптов: положить текст в файл и
  запустить companion самому
  (`codex-companion.mjs task --background --fresh --model gpt-5.6-sol --effort high "$(cat prompt.txt)"`),
  затем `wait-codex.mjs --job <id>`.
- **`status=failed` — не повод начинать ревью заново.** Модель падала на
  последнем шаге («Selected model is at capacity»), и 22 минуты работы выглядели
  потерянными, хотя часть находок лежала в логе задания (`Assistant message` по
  ходу прогона). Порядок: читать `logFile`, затем добирать `--resume` с промптом
  «ничего не искать заново, оформить уже найденное».
- **Молчащее ожидание — повод посмотреть вывод, а не ждать дальше.** Скрипт раз
  в минуту печатает `CODEX_WAIT` с тем, за чем следит; пустой файл вывода
  означает, что процесс умер, а не что задание идёт.
- **Готовность определять по статусу companion, а не по строке в логе.** Маркер в
  логе плавает: 2 августа 2026 ревью закончилось строкой
  `Turn completion inferred after the main thread finished`, а ожидание строки
  `Turn completed.` провисело на готовом отчёте до пинка владельца. Структурный
  признак — задание ушло из `.running[]` в `.latestFinished` со
  `status: "completed"` (`codex-companion.mjs status --json`); это и делает
  `wait-codex.mjs`.
- **Путь к логу брать из companion, а не угадывать.** Форвардер возвращает то
  `<tasks>/<bash-id>.output`, то codex-job-id — по второму файла в `<tasks>/` нет,
  и ожидание молча висит на несуществующем пути (проверено 30 июля 2026: ревью
  пролежало готовым, пока не пнул владелец). Надёжно: поле `logFile` из
  `.running[]` / `.latestFinished`. Тот же вывод даёт `status`, `pid` и
  `createdAt` — по ним отличать свежее задание от прошлого.
- **Профилей плагинов на машине несколько** (`~/.claude`, `~/.claude-team1…3`), и
  companion с каталогом заданий у каждого свой: задание прошлой сессии может
  лежать в одном профиле, текущей — в другом. Активный профиль указывает
  `CLAUDE_PLUGIN_DATA` (`$CLAUDE_PLUGIN_ROOT` в оболочке не выставлен); искать
  companion `find`ом, а не по зашитому пути. `wait-codex.mjs` это уже делает.

### Ревью законченной работы

Ревью у Codex проходит **каждая** законченная правка — это внешний читатель, а не
линтер.

- **Все проверки прогонять до передачи** (см. «Проверки» ниже) плюс живую
  верификацию, если правка того требует. В промпте писать прямо: проверки
  прогнаны и зелёные, повторно не запускать, смотреть код и решения. Без этого
  Codex уходит перепрогонять `vitest`/`lint`/`prettier`/`dev:build` и умирает в
  фазе `verifying`, не выдав отчёта (проверено: 43 минуты и смерть против 9:45 с
  запретом).
- **Diff не пересказывать и не вставлять** — Codex снимает его сам. От меня
  нужна задача: что за пункт, что сделано, какие решения приняты и почему, где
  лежит раздел документации.
- **Ревью свободное.** Не сводить к чеклисту вопросов и не задавать формат
  отчёта — искать он должен там, где сочтёт нужным.
- Найденное перепроверять на своей стороне: Codex бывает неправ (случалось, что
  два вывода из отчёта приходилось поправить по фактам), поэтому принимать
  находки только с подтверждением.
- **Индекс после ревью не трогать.** Проверить `git log --oneline -1`, что коммита
  не появилось, — да. Но застейдженные файлы задачи не сбрасывать: однажды я
  принял `A` у новых файлов за нарушение запрета агентом и трижды снёс стейдж,
  сделанный владельцем. Изменение индекса — не улика.
- Companion не замечает смерть дочернего процесса: если `status` держит
  `running`, проверять `ps -p <pid>` из `status --json`, зомби гасить
  `cancel <job-id>` и перезапускать с `--fresh`.

#### Режим «обсудить починку до реализации» (по запросу владельца)

Обычное ревью просит только находки, и починку я делаю сам. Если владелец просит
обсудить починку с Codex заранее — переключаться на расширенный формат: по каждой
находке требовать четыре пункта.

1. **Способ починки** — до уровня файла и функции, с кодом или псевдокодом.
2. **Радиус поражения** — кто ещё вызывает затронутое, какие сценарии правка
   меняет помимо целевого.
3. **Чем может сломаться** — возможный регресс; если вариантов несколько, какой
   предпочитает и почему. Ответ «не чинить, размен в пользу простоты» — валидный.
4. **Как проверить** — различающий тест и мутация к нему.

Зачем: без этого ревью работает как отложенный тест. В одной из задач по сессиям
билдера две из четырёх находок поздних раундов оказались регрессиями от правок,
которыми закрывались находки предыдущего раунда (обесценивание списка страниц
лишило `publishPage` способа узнать созданную страницу; синхронизация ответа POST
превратила упавший refresh-GET в блокировку повторного сохранения). Следующий
раунд в расширенном формате сэкономил целый круг: разбор пришёл сразу, и края
нашлись до реализации, а не после.

Предложение всё равно взвешивать самому — оно не готовая правка:

- проверять по коду то, о чём Codex не подумал (в раунде 4 он не учёл, что
  существующие спеки могут зависеть от снимаемого `await`, и что список после
  правки должен сохранить `revision`);
- сверять предложенный идиом с `.oxlintrc.json` — предложенный `void promise` в
  проекте запрещён правилом `no-void`, дословное применение дало бы красный линт.

## Проверки

Выбирать проверки по области изменения и сообщать, что было запущено:

- `.ts` / `.vue`: `npm run type-check` и `npx oxlint <changed-files>`;
- стили: `npx stylelint <changed-files>`;
- логика: релевантный `npx vitest run <test-file>`;
- границы импортов: `npm run deps:check`;
- широкие или релизные изменения: `npm run lint:check`, `npm test`, затем при
  необходимости `npm run build`, `npm run dev:build` или подходящий smoke-тест.

Чему в выводе проверок не верить на слово:

- **Проверка типов — только `npm run type-check`.** Голый `npx tsc --noEmit` не
  понимает SFC и сыплет ложными `TS2307: Cannot find module './Component.vue'`.
  Диагностику IDE/LSP тоже сверять с `vue-tsc`: её индекс отстаёт и держит
  удалённые файлы.
- **Зелёные проверки не заменяют живой прогон** там, где дефект молчаливый:
  сломанный SCSS-прелюд обнуляет CSS Modules во всём приложении при зелёном
  `dev:build`, а публичный тип, сославшийся на рантайм-`*.d.ts`, валит только
  `npm run build`.
- Порядок форматирования: `npm run format` перед коммитом. `lint:check` теперь
  включает `format:check`, но хук `.lintstagedrc.cjs` покрывает только
  `*.(ts|js|vue|scss|css)` — дрейф `.md` и `.mjs` коммитом не самолечится.
