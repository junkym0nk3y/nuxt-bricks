# Медиатека: находки ревью

Очередь работ по итогам ревью законченной медиа-части (редизайн галереи,
пользовательские категории, варианты постепенной загрузки, `BricksImage`).
Два независимых прохода — свой и внешним ревьюером; каждая находка перепроверена
по коду, ссылки указывают на состояние файлов на момент ревью.

Проверки на момент ревью: `npm run type-check` и `npm test` (143 файла,
1075 тестов) — зелёные. Линтеры, e2e и соответствие макетам в ревью не входили:
смотрелись кодовая база, качество решений, отказоустойчивость, типизация,
KISS и DRY.

## A. Подтверждённые дефекты

### A1. Поле «Максимальная ширина» невозможно заполнить с клавиатуры — ЗАКРЫТО

`builder/media/components/BuilderMediaGalleryUploadOptions.vue:99-130`

`clampNumber` применяет границы на **каждый** ввод, а `BricksInput`
контролируемый — `ui/inputs/composables/useBricksInput.ts:241-250` синхронизирует
внутреннее значение из пропа. Посимвольный ввод «1920» проверен вживую
(монтирование компонента + `setValue` по цифре):

```
нажали "1" → в поле "16"     нажали "2" → в поле "1692"
нажали "9" → в поле "169"    нажали "0" → в поле "8000"
```

Качество не страдает только потому, что `MEDIA_QUALITY_MIN = 1`. Вдобавок
`BricksInput` клампит по `:min`/`:max` сам на blur
(`useBricksInput.ts:184-198`) — родительский кламп его дублирует.

**Чинить:** отдавать наверх распарсенное число без границ (отсекая только
нечисловое и пустое), границы оставить blur'у `BricksInput` и серверу.

**Сделано.** Родительский кламп заменён парсером без границ и без округления:
пустое и нечисловое оставляют прежнее значение, `0` и дробь проходят как
промежуточное состояние ввода. Осознанный размен: до потери фокуса состояние
поповера может быть невалидным — сервер трактует такое как отсутствие
переопределения либо округляет, а открытие галереи сбрасывает состояние к
конфигу. Строгую валидность дал бы локальный черновик поля с commit на blur;
это заметно больший радиус ради визуального хвоста, и к нему стоит возвращаться,
только если гарантия понадобится сама по себе.

### A2. Компенсация сносит файлы при неопределённом исходе записи — ЗАКРЫТО

`persistence/server/utils/mediaOrchestration.ts:136-151`,
`persistence/server/http/httpClient.ts:120,168`

Любая ошибка `createMedia` трактуется как «записи нет» — удаляются полный файл и
оба варианта. У внешнего backend'а это 10-секундный `AbortSignal.timeout`:
backend успел закоммитить, ответ не доехал — в БД остаётся строка, указывающая на
уже удалённые объекты. У Postgres окно уже (INSERT атомарен), но класс тот же.

**Чинить:** отличать определённый отказ от обрыва. При обрыве не компенсировать, а
свериться `getMediaByUrl` и решать по факту.

**Сделано, но повтором вместо сверки.** Умолчание перевёрнуто: удалять файлы
можно только под явной гарантией `BricksStorageWriteRejectedError`, всё
остальное — неизвестный исход. Приоритет разменов при этом такой: строка в БД,
указывающая на удалённый файл, ломает галерею и опубликованные страницы, а
объект без строки — невидимый мусор, поэтому при неизвестном исходе выбрано
«оставить сироту».

Сверка `getMediaByUrl` из плана заменена одним повтором `createMedia`: метод и
так обязан быть идемпотентным по url, поэтому повтор и находит уже созданную
запись, и создаёт недостающую, тогда как сверка окна незавершённого коммита не
закрывает, а в HTTP-адаптере стоит листинга всей медиатеки. Определённый отказ
ПОВТОРА компенсацию не разрешает: неизвестным исход сделала первая ошибка.

Гарантию ставит адаптер и только вокруг самой вставки. Разрешение конфликта
после `23505` — отдельная фаза без маркера: строка по этому url уже существует,
и таймаут её перечитывания разрешил бы удалить файл из-под живой записи (эта
ошибка была допущена в первой версии правки — `BricksStatementTimeoutError`
наследовал маркер — и снята по ревью). Конфликт уходит в перечитывание, если имя
ограничения совпадает с `uq_bricks_media_url` **или отсутствует**: неназванный
конфликт мог быть и по url, а цена ошибки несимметрична — лишний SELECT против
удалённого файла.

Доказанным отказом считаются классы SQLSTATE `22`, `23`, `42` (сервер разобрал
statement и отверг целиком), неотправленный запрос и остановка вставки серверным
лимитом времени. Не перечень кодов: он дважды оказывался неполным (`22001` от
переросшего колонку MIME, конфликт `bricks_media_pkey`), а каждая дыра — сирота.
Обратное правило «любой SQLSTATE = откат» неверно: `08007` и `40003` прямо
означают неизвестный исход. Обёртка таймаута в маркер потребовала искать его в
цепочке `cause` в `toHttpError` — иначе загрузка теряла бы свой 504.

Контракт внешнего backend'а дополнен разделом «Гарантия исхода записи»: какие
ответы гарантируют отсутствие записи, а какие нет, и что повтор `POST media` с
тем же url обязан вернуть существующую строку.

### A3. Конфигурационный `maxWidth` всё-таки режется границами поля ввода — ЗАКРЫТО

`server/api/bricks/media/upload.post.ts:64-78`

`clampRequestedOptimization` накрывает объект целиком, включая значения, взятые из
`config.optimization`, когда соответствующего поля формы нет. Задокументировано
ровно обратное — `common/constants/mediaOptimization.ts:36-40` и
`persistence/server/utils/imageProcessing.ts:205-215`. `maxWidth: 12000` в конфиге
модуля молча становится 8000 при каждой загрузке через ручку.

**Чинить:** клампить только те поля, которые реально пришли из формы.

**Сделано, но не только этим.** Одной серверной правки не хватило: клиент
отправляет все три поля всегда, поэтому конфигурационная ширина приходила на
сервер как «значение формы» и резалась вместе с ней, а поле ввода схлопывало её
ещё раньше — на blur. Поэтому границы ширины перестали быть константами:
`resolveMediaMaxWidthBounds` считает их от значения конфига, и конфиг диапазон не
сужает, а раздвигает — симметрично в обе стороны, иначе `maxWidth: 8` превращался
бы в 16 при том, что 12000 сохранялся бы. Формула одна на клиент и сервер;
конфигурационная ширина идёт в поповер отдельным пропом, потому что от текущего
редактируемого значения потолок убегал бы вслед за вводом. Серверный хелпер
переименован в `resolveRequestedOptimization` и принимает сырые строки формы:
отличать «поля не было» от «пришло непригодное» обязан тот, кто применяет
границы.

Побочный край, пойманный ревью уже в самой правке: нормализация
конфигурационной ширины обязана быть общей. Отдельное округление на сервере
превращало `maxWidth: 0.4` в ноль, который `sharp` не принимает, а клиент считал
границы от неокруглённого значения и расходился с сервером. Обе стороны переведены
на `resolveConfiguredMaxWidth`; значение меньше пикселя признано опечаткой и
уходит в дефолт — округление вверх сохранило бы его в виде «полного» файла
шириной в один пиксель.

### A4. В базовой миграции два противоречащих абзаца — ЗАКРЫТО

`migrations/0001_init.sql:140-155`

Над `bricks_media_categories` остался текст отменённого решения («Системные
категории неудаляемы, и `other` среди них — приёмник…», «для системных это ключ
i18n») прямо перед новым «предустановленных нет, неудаляемых тоже». Миграция —
источник правды о схеме, два противоречащих абзаца хуже, чем ни одного.

**Чинить:** снять абзац отменённой модели.

**Сделано, плюс третья ошибка в том же блоке.** Абзац отменённой модели снят,
история появления таблицы («прежде набор был хардкодом в UI-константе») оставлена
— она объясняет, зачем таблица вообще нужна. Судьба файлов при удалении категории
сюда не переехала: она уже точно описана у самого FK, а второе место со временем
разошлось бы с первым — ровно так эта находка и появилась.

Заодно исправлено утверждение, которое ревью не заметило: slug «уезжает в URL
фильтра» — неправда, `getQuery` в ручках медиа нет вовсе, фильтрация целиком
клиентская. И «slug считает сервер» уточнено до «сервер nuxt-bricks»: slug
считает `mediaCategoryLabelToSlug` в `mediaPayloadValidation`, а внешний backend
получает готовое значение и переопределять его не вправе.

Правка комментария меняет SHA-256 файла, поэтому строка `0001_init.sql` в
`bricks_schema_migrations` пересчитана вручную: drift-контроль хеширует файл
целиком и на комментарии реагирует так же, как на DDL. До пересчёта
`bricks:migrate status` показывал `[drift]`, после — `1 applied, 0 pending`.

### A5. Контракт внешнего backend'а противоречит схеме — ЗАКРЫТО

`docs/external-backend-contract.md:211` против `:274`

В таблице **обязательных** полей `IMediaItem` категория объявлена как `string`,
а ниже сказано, что она допускает `null`, и код отдаёт `null`. Backend,
реализованный по таблице, закономерно отклонит загрузку без категории.

**Чинить:** привести тип в таблице к `string | null`.

**Сделано, и разнесённые утверждения сведены в одно.** Тип в таблице —
`string | null`, а «FK на slug» заменено на «slug существующей категории»:
внешний backend не обязан быть реляционным, контракт требует поведения, а не
механизма хранения. Абзац из другого конца файла удалён, вместо него — одно
нормативное пояснение сразу под таблицей: расхождение прожило так долго именно
потому, что тип и его оговорка стояли в семидесяти строках друг от друга.

Опциональным поле не сделано, хотя соблазн был: browser-facing multipart без
категории поля действительно не содержит (`media.ts` не кладёт пустую строку), но
`upload.post.ts` превращает его отсутствие в `null` **до** server-to-server
запроса, а `httpClient` сериализует payload обычным `JSON.stringify` — ключ
уходит внешнему backend'у всегда. `category?` в контракте разрешил бы backend'у
принимать отсутствие ключа, которого nuxt-bricks не присылает. Разница слоёв и
записана явно — прежняя формулировка выдавала multipart за payload backend'а.

PATCH описан там же и с обратным правилом: ключ необязателен, отсутствие значит
«не менять», `null` — «снять» (ровно так различает `validateUpdateMediaPayload`).
Сводную таблицу ручек не трогал: длинная ячейка заставила бы prettier
переформатировать все её строки ради одного уточнения, а место для семантики —
проза раздела.

Автоматической сверки контракта с типами в проекте нет и заводить её парсингом
markdown-таблицы не стоит. Поведенческий тест на то, что `createMedia` шлёт
собственный ключ `"category": null`, а не опускает его, — разумный кандидат, но
это уже не документационный долг.

### A6. Пустая строка в `previewUrl` / `mockUrl` рвёт плитку — ЗАКРЫТО

`builder/media/stores/media.ts:53-55`,
`builder/media/components/BuilderMediaGalleryGrid.vue:70`,
`builder/media/components/BuilderMediaGalleryMetaPanel.vue:209`

Нормализация использует `??`, в отличие от соседних `category` и `mimeType`
с `||`, а потребители берут `item.previewUrl ?? item.url`. Пустая строка от
внешнего backend'а даёт `<img src="">` — запрос на саму страницу и битая
картинка.

**Чинить:** нормализовать через `||`, как соседние поля.

**Сделано.** `previewUrl`/`mockUrl` переведены на `||`. Размеры осознанно
остались на `??`: ноль там — полученное значение, а не «неизвестно», и его
пригодность проверяет сам потребитель строгой положительностью. Потребители
(`previewUrl ?? url` в плитке и мини-превью панели) не ужесточались: обе
поверхности берут элементы из одного стора, и вторая проверка размыла бы
инвариант — регресс нормализатора остался бы незамеченным, потому что часть UI
продолжила бы работать. Пустой `item.url` остаётся незакрытым и в эту правку не
входит: корректного fallback у основного адреса нет (превью ушло бы в
сохранённую схему уменьшенным), а ломает он не только плитку, но и выбор,
лайтбокс и ключ идемпотентности — это отдельный вопрос о runtime-валидации
обязательных полей элемента, где сейчас сознательно проверяется только envelope
ответа.

### A7. Backfill: непроверенный результат UPDATE и сироты

`scripts/backfill-media-variants.mjs:245,330`

Варианты кладутся в хранилище до UPDATE и без компенсации: отказ второго PUT или
БД оставляет уже загруженные объекты без ссылок. Если строку удалили во время
прохода, UPDATE затронет ноль строк, но результат не проверяется — запись
считается обновлённой, а оба варианта остаются постоянными сиротами.

**Чинить:** проверять `rowCount` и при нуле удалять только что загруженные
объекты; тот же откат — при отказе второго PUT.

### A8. Очистка имени файла вешает поле навсегда — ЗАКРЫТО

`builder/media/components/BuilderMediaGalleryMetaPanel.vue:108-121`

Пустое имя не отправляется (сервер требует минимум один символ), но и не
возвращается к серверному значению: черновик больше никогда не совпадёт с
теневым значением, то есть внешние обновления имени в это поле уже не доедут —
ровно та регрессия, от которой сторож черновиков и защищает. То же при вводе с
хвостовым пробелом.

**Чинить:** невалидную правку возвращать к серверному значению вместе с
синхронизацией теневого ref'а.

**Сделано, теневой ref трогать не пришлось.** `handleMetaCommit` приводит оба
черновика к отправляемому виду до всякой проверки: имя — к своему `trim()` или к
серверному значению, если после обрезки пусто; alt — к `trim()`. Дальше
сравнение и отправка идут уже по каноническим значениям. Отдельная
синхронизация теневых ref'ов оказалась лишней: сторож в конце каждого прогона
пишет в них серверное значение и слушает его сам, поэтому возврат черновика к
серверному значению сразу даёт совпадение. Починка сделана на commit'е, а не в
самом стороже (сравнение теневого значения с `trim()` черновика) осознанно: поле
осталось бы визуально неканоническим до следующего серверного обновления, сторож
начал бы знать правила валидности имени, а alt, отличающийся одними пробелами,
считался бы нетронутым ещё во время набора и мог быть перетёрт внешним
обновлением. Молчаливый возврат очищенного имени принят как достаточный: тост
для локально невалидного ввода шумен, а панель тостами и не владеет; если явная
обратная связь понадобится, это inline-валидация обязательности поля, а не новый
контроллерный тост.

Соседний край, в эту правку не входящий: PATCH'и метаданных не сериализованы,
поэтому два быстрых commit'а могут разъехаться ответами. Это ровно B2, и правка
его не создаёт и не закрывает.

### A9. MIME из запроса уходит в базу без границы длины

`persistence/server/utils/mediaProcessing.ts:291-295`,
`persistence/server/utils/imageProcessing.ts:126`

`isImageFile` принимает любую строку с префиксом `image/`, а SVG-ветка кладёт в
запись `file.type` как есть — при том, что `mime_type` в `bricks_media` объявлен
как `VARCHAR(255)`. Загрузка `.svg` с длинным `Content-Type` проходит валидацию,
занимает место в бакете и падает на вставке с `22001`.

Живучесть записи это уже не ломает (класс `22` признан доказанным отказом, файл
компенсируется), но пользователь получает generic 500 вместо внятного отказа, а
заливка в хранилище делается зря.

**Чинить:** канонизировать MIME SVG в `image/svg+xml` либо валидировать длину до
обработки файла. Найдено при ревью живучести записи и осознанно вынесено из неё:
это пробел валидации ввода, существовавший до той работы.

### A10. Интеграционный smoke грузит файл в несуществующую категорию

`scripts/integration-lifecycle.mjs:98`

Media-этап отправляет `category: 'other'` и нигде эту категорию не создаёт —
след отменённой модели, где `other` был предустановленным приёмником. На чистой
базе предустановленных категорий нет, поэтому `assertKnownMediaCategory` ответит
400 `UNKNOWN_MEDIA_CATEGORY` и этап упадёт. Сейчас smoke зелёный только там, где
категория с таким slug'ом осталась в базе от ручных прогонов.

**Чинить:** заводить категорию этапом выше либо грузить без поля `category`
(`null` — законное состояние). Найдено при разборе хвостов отменённой модели.

## B. Гонки и живучесть

### B1. Ingress допускает многогигабайтное буферизование

`server/api/bricks/media/upload.post.ts:42,213`,
`persistence/server/utils/requestBodyLimits.ts:55,179`

Лимит 30 запросов в минуту на IP не ограничивает число **одновременных**. Потолок
тела берётся по максимуму видео (~101 МБ), а лимит изображения в 10 МБ
проверяется уже после разбора формы; тело собирается в память целиком и затем
копируется ещё раз в `Response(...).formData()`.

Ручка за auth-middleware (`/api/bricks/**` защищён целиком), поэтому это
authenticated-DoS, а не открытая дыра.

**Чинить:** потолок одновременных загрузок и ранняя проверка `Content-Length`
против типа файла.

### B2. Записи не защищены generation-guard'ом, в отличие от чтений

`builder/media/stores/media.ts:182,326`,
`builder/media/stores/mediaCategories.ts:196`

У `loadItems` есть `itemsRequestId`, у PATCH'ей — ничего. Два быстрых `focusout`
по одному полю разъезжаются: поздний ответ раннего запроса кладёт в стор
устаревшее значение. Отдельный случай: `clearCategoryLocally` снял категорию, а
долетевший ответ более раннего PATCH возвращает в элемент уже удалённый slug.

**Чинить:** номер записи на элемент (или сериализация записей по id) — тем же
способом, каким отсекаются устаревшие чтения.

### B3. TOCTOU у проверки существования категории — ЗАКРЫТО

`server/api/bricks/media/[id].patch.ts:24`,
`server/api/bricks/media/upload.post.ts:232`

`assertKnownMediaCategory` и последующая запись не в одной транзакции. Удаление
категории между ними даёт `23503`, а маппинга этого кода в проекте нет —
клиент получит 500, ровно то, от чего комментарий в
`persistence/server/utils/mediaCategoryRules.ts:17` обещает защитить. У загрузки
окно включает sharp и S3, то есть вся обработка делается зря.

**Чинить:** маппинг `23503` в 400 (окно закрывать транзакцией необязательно —
достаточно, чтобы результат гонки был внятным).

**Сделано.** `23503` переводится в доменную ошибку `BricksUnknownMediaCategoryError`,
её маппит `toMediaHttpError` в 400 с машиночитаемым кодом, клиент выбирает по
коду локализованный текст (иначе вместо 500 пользователь получил бы англоязычный
400 — половину починки). Ранняя проверка переведена с готовой H3-ошибки на тот же
доменный класс: правило хранилища не обязано знать про статусы, а ранний отказ и
отказ FK обязаны выглядеть одинаково. Внешний backend сообщает то же самое
парой «400 + код»; 400 без кода доменным не считается — выдавать чужую валидацию
за отсутствующую категорию значило бы соврать.

Окно транзакцией не закрывалось: удерживать блокировку категории на время sharp
и заливки в S3 дороже, чем внятно ответить на результат гонки. Ранняя проверка
оставлена — она экономит самую дорогую часть загрузки на честной опечатке.

Ключевая связка с A2: доменная ошибка наследует маркер отвергнутой записи, иначе
каждая такая гонка оставляла бы загруженный файл сиротой.

Имя FK-констрейнта не проверяется: в базовой миграции оно не задано, PostgreSQL
генерирует его сам, и опечатка в ожидаемом имени провалила бы распознавание
молча. Живая БД подтвердила `bricks_media_category_fkey` и то, что внешний ключ
у `bricks_media` сейчас один; появление второго потребует различать их по
`constraint` — условие «маппить только при ненулевой категории» от этого
полностью не страхует.

Гонка проверена вживую, а не только юнитами: незакоммиченный `DELETE` категории
оставляет её видимой для ранней проверки (MVCC), а FK-проверка `UPDATE`'а встаёт
на блокировке до `COMMIT`. Ответ пришёл через 1.42 с — то есть запрос
действительно ждал блокировки и упал уже после коммита — со статусом 400 и кодом
`UNKNOWN_MEDIA_CATEGORY`.

### B4. `S3Client` без таймаутов

`persistence/server/s3/s3PublishAdapter.ts:113-120`

Ни `connectionTimeout`, ни `requestTimeout`: зависший endpoint вешает PUT
насовсем, клиентский abort до AWS SDK не доходит.

Находка **вне диффа этой работы** — пред-существующий долг, который она усилила:
PUT'ов на загрузку стало три вместо одного.

### B5. Варианты грузятся и удаляются последовательно

`persistence/server/utils/mediaOrchestration.ts:120-121,82-97`

Операции независимы, правило проекта прямо требует `Promise.all` — сейчас каждая
загрузка платит лишний round-trip к хранилищу.

### B6. Счётчик перетаскивания без страховки

`builder/media/components/TheBuilderMediaGalleryModal.vue:254-273`

Нет `dragend`/window-фолбэка, оверлей приёмника может залипнуть. Не критично
(`pointer-events: none`, клики проходят насквозь), но видимо.

## D. UX-логика и документационный долг

- **Дубликат категории ловится по подписи**
  (`BuilderMediaGalleryFilters.vue:64-78`), а уникальность сервер считает по
  slug'у: `Ёлка`/`Елка`, `Promo`/`Promo!`, две длинные подписи с одинаковыми
  первыми 50 символами. POST вернёт существующую категорию как успех, поле
  закроется, новой категории не появится и ошибки не будет.
- **Поиск сверяет slug, а не подпись** —
  `TheBuilderMediaGalleryModal.vue:112`: по «Фоны» не найдётся ничего, потому что
  в данных `fony`. Искать нужно по подписи через
  `resolveMediaCategoryLabelBySlug`.
- **`dataTransfer.items.length` считает любые элементы, не только файлы** —
  `TheBuilderMediaGalleryModal.vue:257`: перетаскивание текста разворачивает
  приёмник, а `drop` затем молча ничего не делает (`:287` — тихий return без
  сообщения).
- **Кнопка «Загрузить» гаснет на время загрузки**
  (`BuilderMediaGalleryUploadControls.vue:134`), а плитка-приёмник и drop
  продолжают принимать файлы — очередь это поддерживает, но правило неодинаковое.
- **Мёртвые ключи локалей** от снятой зоны загрузки, в обеих локалях:
  `bricks.media.uploading`, `bricks.media.searchLabel`, `bricks.media.dropHint`,
  `bricks.media.chooseFiles` — ноль упоминаний в `src` и `test`.
- **Устаревшие док-строки после отмены приёмника**:
  `server/api/bricks/media/upload.post.ts:204` («`category` … дефолт `other`»),
  `builder/media/stores/mediaCategories.ts:6-8` («сервер переводит её файлы в
  приёмник»), `persistence/server/utils/mediaPayloadValidation.ts:99-102`
  («фильтр «все» уводит файлы в приёмник»), а также
  `builder/media/stores/mediaCategories.ts:133` («slug считает сервер» — считает
  именно сервер nuxt-bricks, а не внешний backend).
- **Пользовательская статья документации описывает отменённый набор категорий** —
  `builder/documentation/docs/guide/ru/05-media.md:11-21`: таблица перечисляет
  «Иконки / Иллюстрации / Фотографии / Другое» как фиксированные категории, при
  том что предустановленных категорий нет, набор заводит сам пользователь, а
  «Другое» как приёмник отменено. Это единственный хвост отменённой модели,
  который видит конечный пользователь, — приоритет выше остальных пунктов D.
- **Мёртвая ссылка на задачу спринта в контракте** —
  `docs/external-backend-contract.md:259` («локальный browser-facing аналог
  удалён аудитом A-01»). Правило проекта такие ID запрещает: через месяц по
  `A-01` не восстановить ничего. Заменить на сам факт удаления ручки.
- **Галерея монтируется без `v-if`** в билдере и в дашборде публикации, поэтому
  `onMounted` тянет список медиа и категорий при старте, даже если галерею не
  открывают, а при открытии всё грузится повторно. Для файлов это было и раньше
  (список нужен сравнению при импорте схемы), категории добавлены этой работой.

## E. Размены — на решение владельца

- **SSR в progressive-режиме не содержит реального URL картинки** —
  `ui/base/image/BricksImage.vue:106-127,369`: в разметку уходит прозрачный 1×1
  или mock, полный файл появляется только после `IntersectionObserver`,
  `noscript`-варианта нет. Дефолт блока — `two-step`, то есть это поведение
  опубликованных страниц по умолчанию. Размен осознанный (экономия запросов), но
  для индексации картинок и no-JS цена реальная;
  `<noscript><img src></noscript>` закрывает её почти даром.
- **Удаление вариантов best-effort** —
  `persistence/server/utils/mediaOrchestration.ts:82-97`: вторичный объект не
  блокирует удаление файла, но фонового сборщика для осиротевших вариантов нет.
- Уже зафиксированы как осознанные и не пересматриваются: `tabindex="0"` на
  каждой плитке вместо roving tabindex, отсутствие пагинации в `listMedia`,
  `getMedia` через list+find в HTTP-адаптере.

## Что сделано хорошо

- Разбиение адаптеров по шву домена (`postgresMediaMethods` / `httpMediaMethods`)
  и оркестрация на узких `Pick`-контрактах — тестируется без Postgres и S3.

  копии — закрывает целый класс расхождений, а не один случай.

  (`test/persistence/backfillVariantPresets.spec.ts`) — редкий случай, когда
  вынужденная копия константы действительно защищена.

  percent-кодирование, обход вверх по ключу.
- Логика черновиков мета-панели «по полю, а не оптом» — правильное решение
  задачи, у которой оба очевидных варианта не работают.

  обеих локалях.
