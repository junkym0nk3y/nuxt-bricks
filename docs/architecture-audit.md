## Краткий вердикт

Это сильный модульный монолит, а не типичный «компонентный ком»: домены выделены осмысленно, границы зависимостей формализованы и реально проверяются. Самые опасные риски находятся не в UI-структуре, а на границе публикации: публичный и редакторский API смешаны, пользовательский HTML/SVG доходит до рендера без надёжной санитарной обработки, а bootstrap схемы БД не является частью поставки пакета.

До внешнего production-использования нужно закрыть P0 ниже. После этого проект имеет хорошую основу для развития как Nuxt-модуль.

## Верификация аудита (2026-07-10)

Ключевые утверждения независимо перепроверены по коду и локальными командами — 14 из 14 подтверждены, одно с уточнением (SSRF, см. пункт P0 ниже):

- `npm run type-check` — ровно 3 ошибки в заявленных местах (`blockAccordion.definition.ts:22`, `blockSlider.definition.ts:26`, `render/pages/[pagename].vue:117`).
- `npm audit --omit=dev` — 5 находок, включая critical prototype pollution в swiper (fix — breaking upgrade 11→14); high/moderate/low — hono, vite, js-yaml, esbuild.
- Auth только на мутациях — подтверждено (`routeProtection.ts:55-57`); анонимный `GET /api/bricks` отдаёт все страницы с drafts и полной schema (`PAGE_SELECT_FIELDS` включает `schema, published`), `GET /api/bricks/media` — всю медиатеку.
- `v-html` в BlockText/BlockAccordion/BlockSvg без санитизации; DOMPurify/sanitize-html в проекте отсутствуют.
- `readNormalizedBody` проверяет только `typeof body === 'object'`; `requireNumericId` через `Number.parseInt` принимает `"1abc"` как `1` (`handlerHelpers.ts:15,34-45`).
- `files: ["dist"]` — `database/init.sql` в пакет не попадает; `postgresStorageAdapter` делает только `ALTER ... thumbnail_url`, auth-адаптер выполняет `ensureSchema()` на каждый вызов.
- Multipart буферизуется целиком до проверки размера (`s3-image.post.ts:56` → `mediaProcessing.ts:87`); Sharp без `limitInputPixels`.
- S3 `extractKeyFromUrl` проверяет только `endpoint/bucket`-префикс — `deleteFile` может удалить любой ключ бакета (`s3PublishAdapter.ts:72-80,137-151`).
- Dynamic routes, `useApiClient` (base из request host + проброс cookie/x-forwarded-\*), `useBuilderPagenameSync` (`history.replaceState`) — подтверждены по коду.

**Оговорка к P0-scope:** versioned migrations и полный public/editorial split обязательны именно для внешнего production-развёртывания / публичного npm-релиза; при внутреннем single-tenant использовании их допустимо сдвинуть в P1. Security-пункты (auth на GET, санитизация, server DTO-валидация) актуальны в любом сценарии.

```text
    ├── runtime/modules/builder
    │   ├── app       — composition root и страницы редактора

```

Поток данных сейчас устроен так: builder и renderer используют один HTTP API; серверные handlers вызывают адаптеры persistence; опубликованный роут сначала загружает список страниц, затем запрашивает конкретную страницу по ID. Это объясняет основные риски: редакторские read-модели становятся публичными, а масштабирование зависит от полного списка страниц.

## Что уже сделано хорошо

- Доменная декомпозиция ясная: builder, render, layouts-blocks, persistence, common и ui разделены по ответственности.
- Правила в .dependency-cruiser.cjs запрещают нежелательные направления зависимостей и циклы; проверка реально включена в lint.
- Render не зависит от builder, а persistence скрыт за IStorageAdapter, IPublishAdapter и IAuthAdapter. Это хорошая база для смены инфраструктуры.
- Для database-auth использованы opaque session token, HttpOnly cookie, SHA-256 хеш токена в БД, scrypt-пароли, timing-safe comparison и защита от перебора.
- Есть unit-тесты для истории, нормализации, publish workflow, ограничителя логина, route protection и SQL query builder.
- Асинхронная загрузка тяжёлых UI-частей и блоков уже используется; проект понимает проблему размера published bundle.

## Целевой контракт после P0

### API

```text
Public
  GET /api/bricks/public/pages/:pagename
    → только published page, safe public projection

Editorial (auth + RBAC позже)
  GET/POST/PATCH/DELETE /api/bricks/admin/pages
  GET/POST/PATCH/DELETE /api/bricks/admin/media

Internal server code
  renderer → storage adapter напрямую или через public read service
  builder  → editorial API
```

У public и editorial endpoint должны быть разные DTO. Public DTO не должен содержать draft fields, private metadata, editor-only URL, credential-bearing data source configuration или arbitrary raw HTML без санитарной обработки.

### Данные и миграции

1. Миграции создают schema_migrations, pages, media, users и sessions.
2. Deploy job применяет миграции до запуска приложения.
3. Runtime DB user имеет только DML, migrator — DDL.
4. Page получает revision/updatedAt precondition; media получает уникальный object key.
5. S3 object key является внутренним идентификатором, URL вычисляется адаптером.

### Безопасный renderer

1. HTML и inline SVG проходят через один allow-list sanitizer.
2. URL в src/href/style ограничены политикой origin/protocol.
3. Пользовательские data sources не могут делать произвольные server-side запросы.
4. Security regression tests используют сохранённые XSS/SSRF payloads.

## Ограничения аудита

Аудит выполнен по репозиторию и локальным командам.
