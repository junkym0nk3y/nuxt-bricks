## Срочное

### 1. Блокирующий CI-job `npm audit` красный: 8 уязвимостей в prod-зависимостях

**Зачем.** В `.github/workflows/ci.yml` job `audit` запускает
`npm audit --omit=dev` блокирующе, с комментарием «сейчас 0 уязвимостей, держим
планку». Планка пробита: локальный прогон 31 июля даёт 8 уязвимостей — 5 high,
2 moderate, 1 low. Значит следующий push в `main` или PR валится на этом job, и
пока он красный, гейт перестаёт различать «чисто» и «появилось новое».

Не все они теоретические. `sharp` — прямая зависимость, обрабатывает **загруженные
пользователем** изображения (миниатюры, обработка медиа); четыре CVE в libvips
приходят ровно на этот путь. `linkify-it` (quadratic DoS на `mailto:`-сканере)
приезжает с `markdown-it`, которым рендерится документация билдера.

| Пакет                       | Severity | Откуда                                                        |
| --------------------------- | -------- | ------------------------------------------------------------- |
| `sharp@0.34.5`              | high     | прямая зависимость                                            |
| `postcss`                   | high     | `@nuxtjs/i18n` → `vite` / `@vue/compiler-sfc`                 |
| `linkify-it@5.0.1`          | high     | `markdown-it@14.2.0`                                          |
| `fast-uri`                  | high     | `vanilla-jsoneditor` → `ajv` (peer)                           |
| `brace-expansion`           | high     | `@kalimahapps/vue-icons` → `@typescript-eslint/parser` (peer) |
| `@hono/node-server`         | moderate | `@kalimahapps/vue-icons` → `@modelcontextprotocol/sdk` (peer) |
| `@modelcontextprotocol/sdk` | moderate | `@kalimahapps/vue-icons` (peer)                               |
| `body-parser`               | low      | транзитив                                                     |

**Что менять.** Семь из восьми `npm audit` чинит в пределах semver — обновлением
lock-файла, без правок кода. `sharp` требует мажора `0.34.5 → 0.35.3`: смотреть
changelog по API обработки изображений, прогонять `smoke:integration` (там MinIO и
реальная загрузка) и проверять сборку под нативные бинарники. Отдельно решить, что
делать с peer-зависимостями, которые тащат в prod-дерево потребителя
`@typescript-eslint/parser` и MCP SDK ради иконок, — три из восьми уязвимостей
приходят оттуда.

**Профит.** Гейт снова работает как сигнал, а не как известный красный. Закрывается
путь «загруженная картинка → libvips» — единственный в списке, где вход
контролирует посторонний.

**Сложность.** Низкая для семи пунктов (обновление лока + прогон проверок), средняя
для `sharp` — мажор на нативной библиотеке, нужен прогон интеграционного smoke, а не
только unit-тестов.

## Технический долг

### 2. Параметры scrypt ниже минимума OWASP

**Файлы:** `src/runtime/server/utils/auth/passwords.ts`, `src/cli/bricks-hash-password.mjs`.

**Зачем.** Используется `N=2^14, r=8, p=1` (`SCRYPT_N = 16384`). Рекомендация OWASP
для scrypt начинается с `N=2^17, r=8, p=1` либо эквивалентных trade-off конфигураций
(`N=2^14` в них идёт с `p=5`). Практический риск низкий: формат хеша
самоописывающий (`scrypt:N:r:p:salt:hash`), verify берёт параметры из самой строки,
поэтому смена дефолта не ломает существующие записи.

**Что менять.**

- Бенчмарк на минимальном production-инстансе, выбрать baseline.
- `N=2^17` при `r=8` требует ≈134 МБ на одну деривацию (`128·N·r`), а дефолтный
  `maxmem` у node — 32 МБ: без явного `maxmem` в опциях `scrypt` вызов просто
  упадёт. Правится в двух местах — рантайм и CLI, они зеркалят параметры.
- Согласовать с bounded-семафором `scryptGate.ts`: сейчас `maxConcurrent = 4`, что
  при 134 МБ на деривацию даёт пик ≈536 МБ RSS только на логинах. Либо снижать
  одновременность, либо осознанно закладывать память.
- Перегенерировать `DUMMY_PASSWORD_HASH` с новыми параметрами. Иначе анти-enumeration
  ломается наоборот: ответ на несуществующий username станет заметно **быстрее**
  ответа на существующий.
- Rehash-on-login: после успешного verify, если параметры хеша ниже текущих, —
  перехешировать и обновить строку. В `IAuthAdapter` метода записи пароля нет
  (`getUserByUsername` только читает), значит расширяется интерфейс адаптера, а
  вместе с ним — `docs/external-backend-contract.md` и внешняя реализация.

**Профит.** Соответствие рекомендации без принудительного сброса паролей: старые
хеши мигрируют молча при первом входе.

**Сложность.** Средняя. Кода немного, но правка расширяет публичный контракт
адаптера и меняет профиль памяти на пути логина — то есть требует замера, а не
только редактирования констант.

### 3. CLI пароля: утечка локальным наблюдателям и SQL, неприменимый к смене пароля

**Файлы:** `src/cli/bricks-hash-password.mjs`, `README.md`.

**Зачем.** Две разные проблемы в одном файле.

Утечка: `README.md:323` учит `npx bricks-hash-password mypassword --username admin`
— пароль остаётся в истории шелла и виден в списке процессов всем локальным
пользователям. Интерактивная ветка не лучше: `promptPassword()` использует обычный
`readline.question()`, то есть печатает ввод эхом на экран.

Неприменимость: CLI печатает `INSERT INTO bricks_users …`, который для уже
существующего пользователя падает на `UNIQUE (username)`. Сценарий «сменить пароль»
— основной, а не первичная установка, — документацией не покрыт вообще. Вторая
половина того же сценария тоже нигде не сказана: смена пароля **не разлогинивает**.
Проверка сессии (`postgresAuthAdapter.ts:48`) джойнит `bricks_sessions × bricks_users`
только по `expires_at > NOW()` и `is_active`, хеш пароля в ней не участвует, так что
украденная кука живёт до истечения `sessionMaxAgeSeconds` (по умолчанию 7 суток) с
любым новым паролем.

**Что менять.** Скрытый TTY-ввод с подтверждением; чтение из stdin или файлового
дескриптора для автоматизации; позиционный пароль по умолчанию отклонять. Печатать
не голый `INSERT`, а upsert (`ON CONFLICT (username) DO UPDATE`) плюс `DELETE FROM
bricks_sessions` по этому пользователю — тогда вывод годится и для смены. Обновить
README обоими сценариями.

**Профит.** Пароль перестаёт светиться в истории и `ps`; операция «сменить пароль
админу» выполняется копипастом из вывода CLI, а не собирается по кускам.

**Сложность.** Низкая — один файл и раздел README. Единственная тонкость — скрытый
ввод: мьютить эхо у `readline` или работать с TTY в raw-режиме, не сломав пайп
(`echo pw | bricks-hash-password --stdin`).

### 4. Медиа-UI недоступен с клавиатуры и скринридера

**Файлы:** `BuilderShellSidebarPropertyImageGalleryEditor.vue` (строки 203, 270),
`BuilderMediaGalleryPreviewLightbox.vue`, `BuilderMediaGalleryGrid.vue`,
локали `src/runtime/locales/{ru,en}.json`.

**Зачем.** Замена изображения и empty state — кликабельные `div` без роли кнопки и
без обработчика клавиатуры: до них нельзя добраться табом и нельзя нажать. Часть
icon-only кнопок без доступного имени — скринридер читает пустоту. Лайтбокс не
объявлен диалогом, не закрывается по Escape, не удерживает фокус и не возвращает его
инициатору: закрыв превью, пользователь клавиатуры оказывается в начале документа.

**Что менять.** `div@click` → настоящие `button type="button"`; локализованные
`aria-label` для icon-only кнопок; лайтбоксу — паттерн модального диалога с
focus trap, возвратом фокуса и Escape. Переизобретать не нужно: в проекте уже есть
`ui/base/modal/BricksModal.vue` на `reka-ui`, у которого это встроено, — сначала
проверить, переиспользуется ли он под лайтбокс.

**Профит.** Галерея становится проходимой клавиатурой и озвучиваемой; поверхность
перестаёт быть тем местом, из-за которого нельзя включить a11y-проверки в CI
(пункт 5).

**Сложность.** Низкая-средняя. Правки механические, но их три файла и проверять
надо руками — табом и скринридером, автотест «фокус вернулся инициатору» пишется
дольше самой правки.

### 5. Хвосты релизного гейта: axe, пороги покрытия, непокрытые сценарии

**Файлы:** `e2e/specs/`, `vitest.config.ts`, `.github/workflows/ci.yml`.

**Зачем.** Браузерный гейт есть, но из заявленного полного lifecycle не покрыто:
вход (фикстура поднята на `auth.mode: 'basic'`, шага логина в спеках нет), импорт,
публикация из UI, конфликт версий и восстановление после него. Axe-проверок нет
вовсе, то есть регрессия доступности проходит молча. Порогов покрытия для
security/persistence/session тоже нет: в `vitest.config.ts` секции `coverage` не
существует, `@vitest/coverage-v8` не установлен.

**Что менять.** Дописать недостающие сценарии; подключить `@axe-core/playwright` на
двух-трёх ключевых экранах; включить coverage v8 с порогами по каталогам, а не
глобально.

**Профит.** Гейт начинает ловить именно те классы дефектов, которые уже ломались
вживую (сессии, поздние ответы сохранения), и перестаёт пропускать a11y-регрессии.

**Сложность.** Средняя, и с оговоркой по очерёдности. Сценарий конфликта версий
требует управляемой гонки — образец уже написан в спеке про опоздавший save, так что
это работа по образцу. А вот пороги покрытия ставить **до** сокращения тестового
набора нельзя: набор признан избыточным и планируется срез порядка 90%, пороги
зафиксируют ровно то, что собираются вырезать.

### 6. npm-пакет не готов юридически и операционно

**Блокер публичного релиза.** **Файлы:** `package.json`, корень репозитория.

**Зачем.** `package.json` объявляет `"license": "MIT"`, но файла `LICENSE` нет ни в
корне, ни в `files`, то есть и в tarball. Поле `repository` указывает
`saintfr3ak/nuxt-bricks`, а `git remote` — `junkym0nk3y/nuxt-bricks`: у публикации
будет ссылка не туда. Нет `CHANGELOG.md`, `SECURITY.md`, `CONTRIBUTING.md` и release
workflow — сообщить об уязвимости и понять, что изменилось между версиями, некуда и
нечем.

**Что менять.** Подтвердить правообладателя и лицензию, положить `LICENSE` в корень
и в `files`, исправить `repository`/`homepage`/`bugs`, завести changelog и контакт
для security, собрать release workflow с provenance, повторно прогнать
`npm run smoke:pack`.

**Профит.** Снимается единственный блокер публикации, который нельзя обойти кодом.

**Сложность.** Низкая по объёму работ, но упирается в решение владельца: кто
правообладатель, под какой лицензией и какой репозиторий считать публичным.

### 7. Вес редактора не под бюджетом

**Файлы:** `scripts/bundle-budget.mjs`, `builder/shell/sidebar/utils/propertyEditorComponents.ts`.

**Зачем.** Бюджеты закрывают две поверхности — entry (112 KB gzip при потолке 122) и
published-страницу (124 при 132). Редактор не закрыт ничем, и наивное расширение
скрипта третьей поверхностью проблему не решит: замер по манифесту даёт для роута
`builder/app/pages/builder.vue` **112 KB в 2 чанках** — ровно entry. Страница
редактора — тонкая оболочка, всё содержимое приезжает через `defineAsyncComponent`,
поэтому такой «бюджет» был бы зелёным всегда и не мерил бы ничего.

Фактический вес поддерева (`builder` + `text-editor` + `ui`) сверх entry — **571 KB
gzip в 54 чанках**, из них 309 KB (54%) — один ленивый вендорный чанк
`vanilla-jsoneditor` под редактор JSON-свойства. Он же тянет `ajv` → `fast-uri` из
пункта 1.

Сборка сейчас печатает три предупреждения о смешанных импортах — компонент
одновременно статический и динамический, code splitting для него не работает:
`ui/inputs/BricksHexInput.vue` (динамический из `propertyEditorComponents.ts`,
статический из `BuilderShellSidebarPublishView.vue`), `ui/inputs/BricksSelect.vue`
(статический из `BuilderShellSidebarPublishView.vue`),
`ui/base/checkbox/BricksCheckbox.vue` (статический из
`BuilderCanvasItemContextMenu.vue`). Плюс штатное «Some chunks are larger than
500 kB» — это про тот же json-редактор.

**Что менять.** Выбрать метрику, которая ловит рост: сумма чанков поддерева
`builder/**` либо реально переданный по сети JS после интерактива редактора (второе
теперь дёшево — e2e-инфраструктура уже есть). Добавить её поверхностью в
`scripts/bundle-budget.mjs` и в CI. Расшить три смешанных импорта — либо статически
импортировать эти три компонента везде, либо динамически везде. Отдельным решением —
нужен ли `vanilla-jsoneditor` вообще: 309 KB gzip ради редактора JSON-свойства.

**Профит.** Рост редактора перестаёт быть невидимым — сейчас в него можно добавить
мегабайт, и ни одна проверка не заметит. Отказ от json-редактора одним движением
снимает половину веса поддерева и одну уязвимость из пункта 1.

**Сложность.** Средняя. Скрипт и смешанные импорты — работа на вечер; спор о метрике
и о судьбе json-редактора — нет, там нужно решение.

**Сложность.** Низкая по действиям, но результат не в нашей власти: две из трёх
цепочек чинятся только апстримом.

### 9. Тёмная тема в макете: цветные кнопки и Confirm Modal расходятся с кодом

**Зачем.** Найдено при отрисовке концепта импорта/экспорта схемы (страница
«📦 Schema Actions», файл `FsPQKxtsHrbJiyiyal9ZlR`): в тёмном режиме подпись на
синей кнопке уходит в тёмный, а модалка подтверждения остаётся белой со светлым
текстом — нечитаемо. Причина не в концепте, а в библиотеке:

- в сете `Button` (`16:62`) подписи вариантов Primary и Danger привязаны к
  `color/base/0`, тогда как код красит их `var(--bricks-static-white)`
  (`BricksButton.vue`, `._primary`/`._danger`). `base/0` — это фон, в тёмном моде
  он тёмный, поэтому текст на цветной кнопке темнеет вместе с ним;
- у компонента `Confirm Modal` (`25:29`) секции `header`/`content`/`actions`
  залиты голым белым без привязки к переменной — в тёмном моде фон не
  переключается. В коде фон даёт корневой `--bricks-base-0`, отдельных заливок у
  секций нет.

**Что менять.** Перепривязать подписи Primary/Danger к `color/static/white`
(шесть вариантов: три размера × два варианта) и заливки трёх секций Confirm Modal
к `color/base/0`. Код — источник истины, правка односторонняя: design ← code.
На странице «Schema Actions» то же уже сделано **оверрайдами внутри инстансов**
(борды `314:20` и `315:236`) — после правки самих компонентов оверрайды снять.

**Профит.** Тёмные копии любых будущих бордов перестают требовать ручной
починки; сверка «макет vs код» по этим компонентам снова показывает нули.

**Сложность.** Низкая: девять привязок, кода не касается. Проверять глазами оба
мода на страницах, где эти компоненты уже стоят.

### 10. Недостающие og-теги и размеры картинки в БД

**Файлы:** `render/pages/[pagename].vue` (`:166-188`),
`persistence/server/postgres/queryBuilders.ts` и `postgresStorageAdapter.ts`,
`common/types/media.d.ts`, `persistence/server/utils/mediaImport.ts`.

**Зачем.** Страница отдаёт `og:title`/`og:description`/`twitter:*`, но не отдаёт
`og:url`, `og:type`, `og:site_name` и размеры картинки, а `twitter:card` появляется
**только** вместе с картинкой — без неё карточка собирается на усмотрение ленты. Без
`og:image:width/height` первый шеринг часто уходит мелкой карточкой: краулер не
дожидается загрузки картинки, чтобы узнать её пропорции.

**Что менять.**

- В мету добавить `og:url` (абсолютный адрес — расчёт нужен и превью выдачи из
  пункта 13), `og:type` = `website`, `twitter:card` = `summary`, когда картинки нет.
- `og:image:width` / `og:image:height` печатать **только когда размеры известны**.
  NULL остаётся у старых строк, у svg и у внешних URL: `social_image` хранит просто
  строку адреса и может указывать на файл, которого в `bricks_media` нет вовсе.
- `og:site_name` — источника нет ни в БД, ни в конфиге. Дешевле опцией модуля
  (`bricks.siteName`), чем таблицей настроек: значение общее для инсталляции, а не
  для страницы. Решить при реализации.

**Схема уже расширена** (3 августа 2026, решение владельца — без новой миграции):
`width`/`height` добавлены в живую БД (`ALTER TABLE bricks_media`) и вписаны в базовую
схему `migrations/0001_init.sql`, строка реестра `bricks_schema_migrations` пересчитана
(`bricks:migrate status` — 6 applied, 0 pending). Осталось по коду: заполнение
`width`/`height` при загрузке медиа, проброс через
`queryBuilders.ts`/`postgresStorageAdapter.ts`, поле в `IMediaItem`, чтение размеров в
мета-тегах. Старым строкам размеры не восстанавливаем — теги для них не печатаются.

**Профит.** Карточка ссылки собирается предсказуемо с первого шеринга; превью
соцкарточки (пункт 14) перестаёт быть оптимистичным.

**Сложность.** Низкая: схема готова, остаётся код.

### 11. Схлопнуть миграции в одну базовую схему

**Файлы:** `migrations/*.sql`, реестр `bricks_schema_migrations` в живой БД, раздел про
миграции в `README.md`.

**Зачем.** Шесть файлов накопились от привычки к forward-миграциям, которая проекту не
нужна: он нигде не опубликован, потребитель базы один, обратная совместимость не
поддерживается. Побочный эффект уже виден — базовая схема разошлась с реальной: в
`0001_init.sql` временные метки объявлены как `TIMESTAMP`, а в живой БД они
`TIMESTAMPTZ` после `0004`. Читать схему приходится, мысленно накатывая пять патчей.

**Что менять.** Свести `0002`–`0006` в `0001_init.sql` — записать **итоговое**
состояние, а не цепочку ALTER'ов: `0004` (timestamptz) и `0005` (namespaced trigger)
переписывают то, что создаёт `0001`, и после слияния должны исчезнуть как отдельные
шаги. Лишние файлы удалить. Реестр привести в соответствие: удалить строки исчезнувших
имён и пересчитать checksum оставшейся — `findMigrationDrift` считает драйфом и правку
файла, и пропажу применённого имени. Проверка — прогон на пустой БД: схема должна
собираться с нуля одним файлом.

**Профит.** Один файл — одна схема; правка схемы перестаёт быть ритуалом с новым
файлом.

**Сложность.** Низкая, но требует внимательности с реестром: на полпути `migrate`
начнёт падать drift'ом, и это ожидаемо.

## Медиатека: размены после ревью

Два осознанных размена, которые ревью медиа-части признало требующими решения, а не
правки по ходу. Оба — про то, чего в коде нет вовсе, а не про ошибку в нём.

### 15. В SSR-разметке нет реального адреса картинки

**Файлы:** `ui/base/image/BricksImage.vue` (`resolveInitialPlaceholder`, шаблон),
`layouts-blocks/components/BlockMedia.vue` (`FALLBACK_LOAD_MODE`).

**Зачем.** При постепенной загрузке серверный рендер отдаёт только слой заглушки:
прозрачный 1×1 (когда пропорция известна), либо превью 480px, либо mock 32px в
режиме `three-step`. Полный `<img>` появляется лишь после того, как
`IntersectionObserver` увидит кадр во вьюпорте, — то есть в разметке адреса
настоящего файла не бывает никогда. Оба слоя вдобавок `alt=""` и
`aria-hidden="true"`: доступное имя живёт на обёртке.

Это дефолтное поведение опубликованных страниц, а не крайний случай: у блока медиа
`FALLBACK_LOAD_MODE` = `two-step`. Цена — индексация картинок (краулер видит 1×1 или
уменьшенное превью) и просмотр без JS, где картинка не появится вообще. Сам размен
осознанный: он экономит запросы и трафик, и отменять его незачем.

**Что менять.** Добавить `<noscript><img src alt></noscript>` рядом со слоями —
браузер без JS покажет полный файл, а краулер получит настоящий адрес. Внутри
`noscript` обязателен именно `alt` (не пустой, как у декоративных слоёв), иначе
разметка отдаст картинку без описания. Проверять на published-странице по сырому
SSR-HTML, а не в dev.

**Профит.** Картинки страниц становятся индексируемыми, страница читаема без JS — при
сохранённой экономии запросов в обычном режиме.

**Сложность.** Низкая: несколько строк шаблона и один e2e/SSR-снимок. Тонкость одна —
не отдать `noscript` в билдере и превью, где он бесполезен, если это окажется дешевле
проверить, чем игнорировать.

### 16. Осиротевшие объекты хранилища некому убрать

**Файлы:** `persistence/server/utils/mediaOrchestration.ts` (`deleteVariantFiles`,
`uploadAndRegisterMedia`), `persistence/server/s3/s3PublishAdapter.ts`
(`discardUnconfirmedObject`).

**Зачем.** Сироты в бакете появляются штатно, и это следствие принятого приоритета:
строка БД, указывающая на удалённый файл, ломает галерею и опубликованные страницы, а
объект без строки — невидимый мусор, поэтому при **неизвестном** исходе записи файлы
сознательно сохраняются. Мест таких несколько: неизвестный исход `createMedia`
(запись могла закоммититься), отказ самой best-effort уборки — и удаление
вариантов, которое не блокирует удаление файла и может не дойти. Каждое из них логируется адресом объекта, но фонового сборщика нет:
уборка держится на том, что кто-то прочитает лог.

**Что менять.** Проход по префиксу медиа (`listFiles` у publish-адаптера уже
пагинирует) с вычитанием адресов, встречающихся в `bricks_media` (`url`,
`preview_url`, `mock_url`). Обязательны две страховки: порог возраста объекта, иначе
сборщик снесёт файл, который прямо сейчас грузится и ещё не зарегистрирован
(окно между PUT и INSERT), и dry-run по умолчанию. Вариант
проще — не сборщик, а отчёт: тот же diff без удаления, и решение по списку принимает
человек. Превью страниц сюда не входят: у них своя уборка по префиксу страницы
(`prunePageThumbnailsAfterUpload`).

**Профит.** Бакет перестаёт расти незаметно, а решение «при неизвестном исходе
оставляем файл» перестаёт быть односторонним — у него появляется вторая половина.

**Сложность.** Низкая для отчёта, средняя для удаляющего прохода: цена ошибки —
удалённый файл живой записи, поэтому нужен порог возраста, dry-run и прогон на
реальном бакете.

## До 1.0 — архитектурные решения

Задокументированные ограничения, требующие явного решения, а не правки.

1. **Single-tenant / RBAC.** Сейчас один уровень editor-доступа: кто вошёл, тот
   может всё. Для SaaS или нескольких редакторов нужны tenant key, ownership и
   проверка прав во **всех** page/media/session-запросах. Профит — возможность
   продавать многопользовательский сценарий; сложность высокая: правка сквозная,
   затрагивает схему БД, каждый серверный обработчик и контракт внешнего backend.
2. **Distributed rate limits.** Лимитеры in-memory и per-process, при нескольких
   репликах лимит умножается на их число. Нужен общий store либо enforcement на
   ingress. Осознанное отступление: внешний shared limiter не реализован, README
   рекомендует закрывать это инфраструктурой. Сложность средняя, но требует выбора
   зависимости (Redis?) и решения, тащить ли её в модуль.
3. **Upload memory sizing.** Multipart буферизуется в памяти целиком. Одновременность
   с 11 августа 2026 ограничена: суммарный объём одновременно буферизуемых форм
   ограничен бюджетом (256 МБ на процесс, переполнение — 503 без чтения тела), и
   резерв держится, пока живы буферы, — то есть до конца заливки в хранилище.
   Осталось решением: расчёт памяти под реальную одновременность при нескольких
   репликах (бюджет per-process, как и rate-лимиты из пункта 2) и вопрос о переходе
   на потоковую загрузку в S3 — только он снимает буферизацию как таковую и делает
   возможной раннюю проверку размера против типа файла (с буферным парсером тип
   части до чтения тела неизвестен). Сложность низкая, если остаёмся на
   документации; средняя-высокая для потоковой загрузки.

## Требования к процессу

Не задачи, а условия для будущих правок.

- **Любая правка на пути «схема → `brickPath` → карта загрузчиков → компонент»
  проверяется published-страницей с настоящим brick-компонентом в prod-сборке**
  (`.output`, запущенный из постороннего cwd), а не только в dev. Компонент и его
  проп из схемы обязаны попадать в сырой SSR-HTML без ошибок гидрации. Причина: в
  dev отклонённый лоадер async-компонента Vue перебрасывает ошибку, и отличить её от
  падения самой страницы нельзя, поэтому дефекты этого класса в dev выглядят мягче,
  чем есть. Проверка снималась 31 июля 2026 — текущее состояние её проходит.
- **Альтернатива резолва отклонена** (27 июля 2026, не начинать без явного
  пересмотра): строить карту загрузчиков из резолвнутых каталогов компонентов,
  заменив `import.meta.glob` на сгенерированный через `addTemplate` модуль. Выгода
  обслуживает сценарии, которых нет ни в одном из трёх поддерживаемых (playground,
  npm-модуль у потребителя, конвенциональные Nuxt 3 и 4), а размен плохой:
  `import.meta.glob` Vite разворачивает одинаково в клиентском и SSR-бандле, тогда
  как `#build/…` резолвится по-разному в dev и prod и по-разному в клиентской и
  серверной сборке — притом что код лежит на SSR-пути published-страниц. Возвращаться
  только если мягкий рестарт на `add`/`unlink` окажется неприемлемо дорогим у
  потребителя или появится реальная потребность в кастомных каталогах и слоях;
  начинать в обоих случаях со спайка на два бинарных вопроса — резолвится ли
  `#build/…` из `dist/runtime/` установленного пакета (проверять на
  `npm run smoke:pack`, не в playground) и находит ли
  `getModulesByFile('virtual:nuxt:<dst>')` модуль шаблона в нашей конфигурации.

## Решения владельца, не правки

- **`test/README.md` отстал от состава спеков.** Файл документирует каждый спек по
  имени, список расходится с диском, и ничем это не проверяется. Отложено
  (28 июля 2026, решение владельца): набор тестов признан избыточным, планируется
  срез порядка 90%, и синхронизация списка обесценится вместе с вырезанными спеками.
  После сокращения дефолт — заменить пофайловый список описанием доменов, чтобы
  новый спек не требовал правки README.
- **`as unknown as` в тестах** — 16 совпадений в 13 файлах (одно из них комментарий о
  том, что приведение как раз убрано). Запрет в `.claude/rules/typescript.md`
  сформулирован без оговорок про `test/`, и ревью по ходу спринта снимало каждое
  новое приведение, то есть де-факто правило на тесты распространили. Вопрос —
  вычищать ли исторические одной отдельной уборкой.
- **Заголовки коммитов** `0295ba5`, `ca593ca`, `6bd51cc`, `d288549`, `b1a6cee`,
  `65bb714`, `260416a`, `1660a90`, `7c5cf32` содержат идентификаторы задач, которые
  то же правило запрещает в сообщениях коммитов. История локальная, переписывание
  возможно.

## Документированные ограничения (не задачи, но помнить)

- Без `bricks.proxy.healthUrl` readiness proxy-пути опирается только на
  reachability-fallback (ответ < 500 считается живым): неверный путь в `PROXY_URL`
  или отсутствующий editorial API на живом хосте не детектируется.
- Средам, успевшим записать старый checksum миграции `0001` новым CLI (внутренние
  стенды ветки), нужен ручной сброс drift'а — путь описан в README. Осиротевшую копию
  `update_updated_at_column()` после миграции `0005` оператор убирает вручную.
- Smoke- и integration-гейты не заменяют внешний penetration test, DAST и нагрузочные
  испытания.
