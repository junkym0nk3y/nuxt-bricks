## 1. Резолв brick-компонентов: контракт путей и транспорт манифеста

**Тип:** исправление (механизм не работал вовсе) + смена транспорта.

**Зачем.** Резолв был сломан по построению: ключи `import.meta.glob` — всегда
`/components/<путь>.brick.ts` (Vite root = `srcDir`), а генератор сканировал от
`process.cwd()` и писал в манифест `../playground/components/…`. Совпасть они не
могли; ~100 строк `generatePathVariations` перебирали варианты пути и не
находили ничего, параметр `isPlayground` был мёртвым.

**Что сделано.** Единый контракт: `brickPath` == ключ glob == `/` + путь
относительно `srcDir`, один паттерн `components/**/*.brick.ts`, прямой lookup без
вариантов. Манифест уехал из `public/bricks.json` (чтение через `process.cwd()`) в
`<buildDir>/nuxt-bricks-manifest/manifest.json` + Nitro `serverAssets`, генерация —
в хуке `build:before`. Namespace и каталог квалифицированы именем пакета: короткое
`bricks` давало реалистичную коллизию с потребителем, причём в dev это был отказ
**всего** Nitro-сервера (`already mounted at bricks:`), а в prod — тихое слияние
файлов в один namespace.

Генерация сериализована очередью (один скан на инстанс Nuxt, заявки склеиваются в
один догоняющий прогон), публикация атомарна (запись во временный файл + `rename`,
`ignore: ['**/*.tmp']` в монтировании), обработчик вотчера целиком в `try/catch` —
Nuxt зовёт хук без `await`, и любой реджект убивал бы dev-сервер.

**Профит.** Библиотека компонентов работает; деплой одного `.output` из
постороннего cwd работает; недописанный JSON больше не превращается в пустую
библиотеку; чужой файл в `buildDir` не может подменить манифест.

**Файлы:** `src/bricks-manifest.ts`, `src/module.ts` (регион «Манифест
brick-компонентов и dev-вотчер»), `src/runtime/modules/common/constants/brickManifest.ts`,
`src/runtime/modules/common/types/brickManifest.d.ts`,
`src/runtime/server/utils/bricksComponents.ts`,
`src/runtime/modules/common/composables/useBrickImports.ts`.
Удалено: `layers/**` из скана, `generatePathVariations`, CLI `bricks-gen` с

## 2. Dev-вотчер: мягкий рестарт вместо опоры на внутренности vite-node

**Тип:** рефакторинг, снятие технического долга. Поведение к этому моменту уже
работало — заменён рабочий, но хрупкий механизм.

**Зачем.** `import.meta.glob` не подхватывал новые файлы при SSR, и первым
решением было синтетическое событие `server.watcher.emit('all', 'change', …)` по
файлу самого glob-модуля — опора на недокументированную деталь vite-node.

**Что сделано.** Штатный ответ Nuxt на «состав файлов изменился»: `add`/`unlink` →
`nuxt.callHook('restart')` (рестарт сам прогоняет `build:before`), `change` →
перегенерация манифеста + `full-reload`. Фильтр — та же область, что у скана, так
что `*.brick.ts` вне `components/` лишнего рестарта не вызывает. Вотчер
регистрируется и для published-режима: карту загрузчиков читает не только билдер.

**Профит.** Удалено ~100 строк (`src/vite-brick-watch.ts` целиком) вместе со
связкой с двумя Vite-серверами Nuxt. Плата — порядка секунды на `add`/`unlink`
(замерено: Vite client 6–15 мс, Vite server 58–131 мс, Nitro 488–633 мс), но это
редкое событие: файл создают один раз, дальше итерация идёт через `change`.

**Известное ограничение** (записано в код): при явном
`experimental.watcher: 'parcel'` переименование или удаление каталога с
brick-файлами может пройти мимо вотчера — parcel коалесцирует поддерево в одно
событие, теряя признак «каталог». Дефолт Nuxt (`chokidar-granular`/`chokidar`)
эмитит `unlink` по каждому файлу, и фильтр их видит.

**Файлы:** `src/module.ts`, `src/bricks-manifest.ts` (`isBrickFilePath`).
Удалён: `src/vite-brick-watch.ts`.

## 3. Метаданные бриков извлекаются на build-time

**Тип:** фича, ломающая контракт brick-файла (`feat(manifest)!`).

**Зачем.** Билдер импортировал brick-модуль ради `values`, `slots` и
`description` — то есть тянул в бандл Vue-компоненты и стили всей библиотеки
ради данных. Категория при этом добывалась регуляркой по исходнику.

**Что сделано.** Метаданные читаются разбором AST без исполнения модуля
(`oxc-parser`, заявлен прямой зависимостью — транзитивное присутствие через Nuxt
не резолвится в изолированной раскладке pnpm; `typescript` ради полусотни строк
разбора весит 23 МБ против 1.4 МБ). Исполнение модуля отклонено: brick-файл
импортирует `.vue`, то есть потребовал бы Vite-конвейера, которого в prod-сборке
нет.

Язык метаданных закрытый: литералы (строка, конечное число, boolean, `null`,
шаблон без подстановок, массив и объект без spread, вычисляемых ключей, методов и
геттеров), `__proto__` запрещён на любой глубине, `export const` обязателен.
Всё остальное — ошибка сборки с файлом, позицией и путём до поля
(`brick.values.headline.default`). `dataSources` с функциями разбор не трогает.
`values` стало обязательным полем: без него запись молча выглядела бы как
исправный брик без свойств.

**Профит.** Библиотека, панель свойств, слоты, inline-редактирование и список
forceRender-пропов живут из одного индекса. Сайдбар перестал монтироваться под
`v-show` при закрытой панели, то есть карточки больше не грузят все brick-модули
на входе в редактор. Тихая подмена значения невозможна: `1e999` и `-0`
отвергаются сборкой, а не публикуются как `null` и `0`.

**Цена, принятая осознанно:** метаданные обязаны быть литералами в самом
объявлении. Вынесенная константа, вызов функции, мутация объекта после
объявления — рантайм увидит, манифест нет. Ограничение задокументировано в
README как граница контракта.

**Файлы:** `src/brick-literals.ts` (новый), `src/brick-metadata.ts` (новый),
`src/types/brickLiterals.d.ts`, `src/types/brickMetadata.d.ts`,
`src/bricks-manifest.ts`, `useComponentLibrary`, `useComponentEditorMetadata`,
`useCanvasItemLoader`, clipboard-экшены стора. Удалены: `useSidebarBrickDescription`,
`extractBrickSlots`, `normalizeBrickSlots`.

## 4. Прототипные ключи в map-like контейнерах

**Тип:** исправление (класс дефектов вплоть до отказа процесса).

**Зачем.** Категория, id компонента, имя свойства и URL картинки приходят из
схемы страницы или brick-файла и становились ключами обычных объектов. Это не
теория: brick с категорией `__proto__` роняет **всю страницу редактора** в 500
(`grouped[category].push is not a function`), а компонент с `id: "__proto__"` в
published-схеме валит **весь dev-сервер** — `Object.prototype` получает ключ
`headline`, его подхватывает `for...in` в vue-router, и любой запрос отдаёт 500.
Оба воспроизведены живьём.

**Что сделано.** Общий хелпер `common/utils/safeRecord.ts` (`hasOwnKey`,
`readOwnKey`, `toSafeRecord`); контейнеры, ключ которых приходит извне целиком,
переведены на `Map` (проверено, что devalue гоняет `Map` через Nuxt payload
туда-обратно, включая own-ключ `__proto__` внутри карты). Закрыто около двадцати
мест в трёх волнах — серверная ручка и сайдбар, затем восемь мест по ревью, затем
ещё девять, которых не поймал первый шаблон поиска. Отбрасывание own-ключа
`__proto__` сведено в единственную воронку копирования пропсов
(`cloneComponentProps`), а не размазано по утилитам.

**Профит.** Отказ процесса устранён; поведение стало однородным (раньше ветка
«Skip» в резолвере картинок вела себя иначе, чем «заменить»).

**Границы, установленные замерами.** Слот с именем `__proto__` нерендерим в
принципе — `ssrRenderSlotInner` делает `slots[slotName]` по обычному объекту и
падает до нашего кода. Через API такой ключ тоже не приходит: `destr` в ofetch
выбрасывает его сам. Остаётся ручной импорт JSON-файла.

Закрыты именно map-like контейнеры, ключ которых берётся из схемы или
brick-файла: категории, id компонента, имена свойств, URL резолвера картинок,
параметры data source, реестр layout-блоков, карта загрузчиков. Утверждения «во
всём проекте» здесь нет.

**Известное ограничение, принятое осознанно:** `defaultProps` в приложении
читаются через глубоко реактивный прокси Vue, поэтому брик со свойством по имени
члена прототипа (`hasOwnProperty`) получит инструмент Vue вместо своего значения.
Защита от подмены прототипа при этом работает; случай признан пренебрежимым.

**Файлы:** `common/utils/safeRecord.ts` (новый),
`common/utils/bricks/components.ts`, `render/composables/useRendererDataSources.ts`,
`render/composables/useBricksDataSources.ts`, `layouts-blocks/registry.ts`,
`layouts-blocks/utils/responsiveVars.ts`, `builder/shell/sidebar/utils/componentCategories.ts` (новый),
`builder/shell/sidebar/utils/variantBuilders.ts`,
`builder/canvas/item/utils/forceRenderSnapshot.ts` (новый),

## 5. Сессии билдера: правки перестали теряться молча

**Тип:** исправление (потеря пользовательских данных).

**Зачем.** Пять независимых способов потерять работу, найденных цепочкой ревью:

- автосейв черновика был `setTimeout(800)` без слушателя выгрузки — таймер гиб
  вместе со страницей;
- уход из редактора SPA-навигацией вызывал `onScopeDispose`, который
  запланированное сохранение **отбрасывал**;
- после 50 снапшотов истории watch автосейва замолкал навсегда: `capture` поднимал
  индекс до 50, `clampHistory` возвращал на 49 в том же действии, и watch по
  индексу не срабатывал;
- поздний ответ вытесненного открытия писал схему в чужую сессию;
- медленный Save as Copy переименовывал сессию посреди записи.

**Что сделано.** `pagehide` + безусловный сброс (guard на «таймер стоит» выбрасывал
самый частый случай — правку пропса, у которой свой debounce истории 300 мс);
`flushDraft` в `onScopeDispose` и sync-watcher на `routePagename` (обычный
выполнился бы после watcher'а сессии, то есть уже с чужим ключом); watch на ссылку
снапшота вместо индекса; поколение сессии с проверкой после **каждого** await и
инкрементом в `onScopeDispose`; `isSessionRenamable` с учётом `isSubmitting` и
готовности.

Дальше поколение выросло в **токен сессии** (`useBuilderSessionToken`): `capture()`
на старте операции, `isCurrent()` перед записью. Им закрыты Save as Copy поверх
другой страницы, поздняя фиксация снапшота, снимок превью (три границы, решающая —
**после** `await domToBlob`: библиотека сначала ждёт загрузку всех `img`/`video` и
только потом клонирует DOM, то есть внутри окна снимается уже чужой канвас), live
preview, миграция черновика и портальные поверхности.

**Профит.** Все перечисленные сценарии закрыты различающими тестами и
контрольными прогонами: без правки дефект воспроизводится, с правкой — нет.

**Файлы:** `builder/app/composables/useBuilderDraftPersistence.ts`,
`useBuilderSession.ts`, `useBuilderSessionToken.ts` (новый),
`useBuilderPagenameSync.ts`, `useBuilderPage.ts`, `usePageThumbnail.ts`,
`usePreviewSync.ts`, `builder/publish/stores/publish.ts`,
`builder/publish/utils/currentPageWrite.ts` (новый),

## 6. Отказ открытия сессии перестал выглядеть рабочим редактором

**Тип:** фича (новая поверхность UI), закрывающая дефект потери данных.

**Зачем.** Если bootstrap падал на `fetchPageRequest`, `startEditingPage` уже
прошёл: `editingPageId` выставлен, форма заполнена из сводки, канвас пуст. Кнопка
«Сохранить» в этом состоянии отправляла PUT с пустой схемой и **затирала страницу
в БД**. Лоадер не спасал — он закрывает только канвас и прячется через один цикл
анимации (2.4 с) независимо от фактической загрузки.

**Что сделано.** Блокирующий экран (решение владельца — не баннер: баннер
превращает тихую потерю в громкую, но не устраняет) с причиной отказа и кнопками
«Повторить» / «Мои страницы». Рядом — щит на время **любого** незавершённого
открытия, `:inert` на рабочую область (мышь закрывает щит, но не Tab, не
сфокусированное поле и не глобальный `keydown`), guard'ы на глобальные клавиши и
на действия тулбара, лежащего вне щита. Блокировка идёт по готовности сессии, а не
по факту отказа: то же окно открыто на обычной загрузке и на повторе. Правила
сохранения вынесены в утилиту, потому что в composition root они проверялись бы
только по тексту, а текстовый кейс зелен и на потерянном `return`.

Зависший запрос больше не запирает редактор навсегда — `withBootstrapTimeout`
(30 с) уводит сессию в обычное состояние ошибки; брошенное открытие гасится
инкрементом поколения, иначе поздний ответ лёг бы на канвас поверх экрана.

Отдельно закрыт класс запоздалых ответов модалки восстановления черновика:
`force-mount` держит содержимое в DOM до конца leave-анимации, и её кнопки всё это
время работают. `pointer-events: none` на уезжающую модалку **и её потомков**
(кнопки ставят себе `auto`), `inert` императивно в хуке `@leave` (у уезжающего
элемента биндинги шаблона уже не патчатся), привязка ответа к поколению и
одноразовость.

**Профит.** Разрушительное сохранение невозможно; правка в окне незавершённого
открытия не пропадает молча; девять раундов ревью не нашли оставшихся входов.

**Файлы:** `builder/app/components/TheBuilderSessionError.vue` (новый),
`builder/app/utils/sessionGuards.ts` (новый), `builder/app/composables/useBuilderSession.ts`,
`builder/app/pages/[pagename].vue`, `builder/shell/toolbar/components/TheBuilderShellToolbar.vue`,
`ui/base/modal/BricksModal.vue`, `assets/scss/common/transitions.scss`,
`src/runtime/locales/{ru,en}.json`.

## 7. Политика таймаутов: запрос перестал висеть вечно

**Тип:** фича (механизм, которого не было), закрывающая класс зависаний.

**Зачем.** У запросов не было прикладного потолка вовсе. Зависший backend держал
`isSubmitting` и `isUploading` поднятыми, `finally` недостижимым, а посетителя
published-страницы — в бесконечном ожидании. Три места в предыдущих пунктах уже
лечили это локально.

**Что сделано.**

- **Потолок по методу с override на вызове:** чтение 10 с, запись 30 с, отдельно
  `login`/`logout` 10 с, `s3-proxy` 15 с, thumbnail 60 с, media upload 300 с.
  Единственный список read-методов — в `apiRequestPolicy.ts`: от него зависят и
  потолок, и выбор текста. URL внутри политики не разбирается — это была бы вторая
  копия знания о роутах.
- **Потолок ставится живым сигналом всегда.** Первая редакция ставила
  `AbortSignal.timeout` только поверх чужого сигнала, а в остальных случаях
  полагалась на `options.timeout` ofetch — тот снимает таймер вокруг одного лишь
  `await fetch(...)`, то есть **зависшее тело ответа держало запрос вечно**
  (замер: с одним `timeout: 400` запрос не завершился за 2500 мс). Дефект пункта
  был закрыт наполовину, нашло второе ревью.
- **Обрыв записи не выдаётся за отказ.** Тексты разведены по существу: чтение —
  «повторите», запись — «сервер не подтвердил операцию вовремя: она могла
  завершиться». Автоповтора записи нет: для настоящей гарантии нужен idempotency
  key, то есть расширение серверного контракта.
- **Классификация починена под браузер.** Chrome при аборте **во время чтения
  тела** подменяет ошибку на `AbortError` независимо от `reason` — проверено и
  нативным `AbortSignal.timeout`, и своим контроллером; Node (undici) сохраняет
  `reason` на обеих фазах. Обёртка транспорта восстанавливает причину по сигналу:
  судим по `signal.reason`, а не по ошибке, поэтому отмена вызывающего и общий
  дедлайн прогона data sources таймаутами не становятся.
- **SSR: `timeout` там инертен и транспортом не лечится.** Относительные URL уходят
  в `fetchNodeRequestHandler`, а в `node-mock-http` слова `signal` нет вовсе.
  Закрыто дедлайнами промисов вокруг live-lookup'а страницы, прогона data sources
  и запроса манифеста. Таймаут больше не превращается в 404 (закешировался бы у CDN
  и был бы понят краулером как отсутствие страницы) — теперь 504.
- **Неудачный SSR-прогон не оседает в payload как окончательный.** До правки
  ошибка ложилась в `payload._errors`, а при гидрации с ошибкой Nuxt пропускает
  initial fetch — сайдбар оставался пустым до полной перезагрузки, которая снова
  уходила в тот же SSR. Теперь библиотека деградирует до layout-блоков с маркером
  `isPartial`, прогон data sources отчитывается о неполноте, и клиент делает
  **одну** попытку догнать на `onNuxtReady` (ни `refresh()` сразу, ни `onMounted`
  не годятся: `getDefaultCachedData` при `isHydrating` отдаёт тот же payload, а
  mounted-хуки успевают отработать до снятия флага).

**Профит.** Замерено вживую: зависший live-lookup — 504 ровно на 10,0 с вместо
бесконечного ожидания; зависшее тело ответа на дашборде освобождает интерфейс,
тогда как до правки тот же ответ держал «Loading…» больше 28 с; зависший data
source отдаёт страницу за 5,04 с с пропами успевших источников, а после гидрации
клиент догоняет пропавший.

**Методическая ловушка, стоившая целого раунда.** Первая живая проверка имитировала
зависание Nitro-middleware'ом, который молчал **до** ответа, — то есть обе фазы
выглядели одной, и незакрытая фаза чтения тела осталась незамеченной. Имитация
зависшего backend'а обязана иметь второй режим: «заголовки отданы, тело не
досылается». (Сам механизм и оба режима закреплены тестами в
`test/common/apiRequestPolicy.spec.ts`.)

**Вторая ловушка, общая для всей живой проверки рантайма.** Правки в
`src/runtime/**` работающий dev-сервер в SSR-бандл по HMR не подхватывает: три
подряд мутации одного композабла давали одинаковый ответ, пока сервер не был
перезапущен. Мутационные и контрольные прогоны на published-странице делать только
с рестартом `npm run dev`, иначе «прогон на снятой правке» ничего не проверяет.

## 8. Серверный лимит времени SQL

**Тип:** фича (новая опция конфигурации), закрывающая ресурсный дефект.

**Зачем.** Клиентский потолок освобождает ожидающего, но не ресурс: отменённый на
клиенте запрос продолжает занимать соединение из конечного пула. Серия таких
запросов исчерпала бы его — лечение UX превратилось бы в отказ обслуживания.

**Что сделано.** Спайк на живой БД до проектирования показал, чем **не** решается:
`query_timeout` драйвера отвечает вовремя, но запрос остаётся активным на сервере
(видно в `pg_stat_activity`); `idle_in_transaction_session_timeout` не отменяет
запрос, а рвёт сессию, и FATAL приходит асинхронным событием на выданном клиенте —
без отдельного `client.on('error')` это падение процесса.

Работает `statement_timeout`: база сама отменяет запрос, соединение переживает
отмену и переиспользуется пулом. Опция `bricks.database.statementTimeoutMs`
(дефолт 8000 мс), env `NUXT_BRICKS_DATABASE_STATEMENT_TIMEOUT_MS`. Отмена
превращается в доменную `BricksStatementTimeoutError` внутри postgres-модуля (в
HTTP-слое SQLSTATE не появляется) и дальше в 504 с `data.code = STATEMENT_TIMEOUT`.

**Два раунда ушли на то, что защита была дырявой.** `?statement_timeout=0` в строке
подключения не перекрывал значение, а **выключал лимит** — драйвер накладывает
разобранный URL поверх конфигурации. Вычистить параметр из строки не удалось: обход
через `%5F` и через форму, которую `new URL` не разбирает, а драйвер разбирает.
Вывод вместо заплатки: гарантия перенесена туда, где строка уже не участвует —
сессионный `SET` в хуке `onConnect`, которого `pg-pool` дожидается перед выдачей
клиента. Отдельно выяснилось, что `onConnect` появился только в `pg-pool@3.13.0`, а
peer-диапазон допускал `pg ^8.16.0`, где опция игнорируется **без единого сигнала** —
нижняя граница поднята до `^8.20.0` с guard-тестом.

**Профит.** Замерено: чтение под блокировкой — 504 ровно на 8,03 с, следующий
запрос проходит за 17 мс (пул жив). Границы задокументированы в README: лимит не
касается `bricks-migrate` и кастомных адаптеров, а с PgBouncer нужен
`ignore_startup_parameters` плюс лимит на роли — сессионный `SET` надёжен только в
session pooling.

## 9. Отказ доходит до пользователя

**Тип:** исправление (тихие отказы).

**Зачем.** Потолок ожидания превратил зависание в обычный отказ — и стало видно,
что дальше отказ местами теряется. Класс другой: там не завершался запрос, здесь
не доходил результат.

**Что сделано.**

- **Медиатека.** Отказ `loadItems` больше не обнуляет список (transient-отказ
  повторного открытия не стирает показанную галерею); ответ непонятной формы стал
  отказом контракта, а не пустой галереей; отказы записи пробрасываются до тоста;
  `isUploading` стал счётчиком (у двух параллельных загрузок `finally` первой
  снимал индикатор); latest-wins для списка, в том числе против локальных записей.
- **Библиотека компонентов.** Второй загрузчик того же `/api/bricks/components`
  (селектор модалок) устранён вместе с мёртвым фасадом `useModals.ts`; кеш модалок
  наполняется из общего ответа. Отказ виден блоком с повтором, layout-блоки
  остаются доступными. Снимок последней успешной загрузки держим сами: `useAsyncData`
  при отказе сбрасывает `data` в дефолт, то есть неудачный повтор забирал бы уже
  загруженные брики.
- **Auth.** `fetchMe` возвращает `null` только для 401; раньше недоступность
  сервера выглядела как «не авторизован», и форма молча предлагала вход, который
  упёрся бы в тот же сервер.
- **Подтверждения записи.** Определённый отказ (4xx/5xx) оставляет диалог открытым
  — объект на месте, повтор безопасен. Обрыв по потолку диалог закрывает: исход
  неизвестен, и текст прямо просит обновить данные перед повтором.
- **Импорт схемы.** Модалка «найдены новые изображения» показывается только после
  достоверного сравнения с медиатекой: при недоступной медиатеке заголовок и выбор
  «оставить/заменить заглушкой» были ложными. Достоверность отслеживает снимок
  стора — `items.length > 0` для этого не годится, загрузка файла кладёт его в
  список локально.
- **Хранилище черновиков.** Проба `setItem`/`removeItem` на готовности сессии:
  запрет данных сайта иначе обнаружился бы через окно debounce после первой правки,
  когда пользователь уже работает, считая правки защищёнными. Латч — по токену
  сессии, а не по экземпляру страницы. Заодно `getItem`/`removeItem` заведены под
  `try`: при запрещённом хранилище исключение выходило прямо из bootstrap'а, и
  вместо редактора пользователь получал блокирующий экран отказа из-за черновика.
- **Пропущенные брики** (промах glob'а) показываются отдельным блоком, а не
  выбрасываются молча; в dev — с подсказкой про перезапуск.
- **Двойная запись.** `isSubmitting` стал getter'ом над списком id незавершённых
  операций: операция прежней страницы, завершаясь, снимала индикатор у записи на
  открытой.

**Профит.** Ни один из перечисленных отказов больше не тонет. Пять раундов ревью
на последнем пункте; последний находок не дал.

**Методическая ловушка при проверке тостов** (сорвала два замера подряд). Тост
живёт 4 секунды, поэтому снимок DOM, сделанный после действия, показывает «тоста
нет» — наблюдателя надо ставить **до** действия. Рядом вторая: на странице
билдера два viewport'а тостов (собственный и медиа-галереи), и по первому
совпадению селектора читается не тот — искать по владельцу элемента
(`__vueParentComponent`).

## 11. Отсутствующий брик: страница падала целиком, а не рендерила заглушку

**Тип:** исправление (заглушка была написана, но недостижима).

**Зачем.** Если в сохранённой схеме остался компонент, лоадера которого в сборке
нет (файл удалён или переименован), `resolveBrickComponent` всё равно отдавал
`defineAsyncComponent`: промах обнаруживался уже внутри лоадера исключением, а
`errorComponent` задан не был. Ветка `RendererPlaceholder` в рендерере
управления не получала.

**Насколько это было хуже, чем считалось.** Ожидался пустой узел — дыра в
вёрстке. Живая проверка на prod-сборке показала другое: отклонение лоадера
доходит до SSR-рендера и роняет **всю страницу в 500**
(`Module /components/… has no usable component export`). То есть один устаревший
компонент в схеме выносил published-страницу целиком, включая остальные,
исправные компоненты.

Различающей проверкой может быть только prod-сборка. В dev страница тоже отдаёт
500, но там его даёт переброс ошибки самим Vue, и отличить «заглушка не
сработала» от «страница упала» невозможно — до и после правки dev выглядит
одинаково.

**Что сделано.** Лоадер проверяется синхронно, до создания async-компонента:
промах отдаёт `null`, и управление доходит до существующей заглушки с настоящим
именем компонента. Решение одинаково на сервере и клиенте — карта лоадеров
разворачивается из одного паттерна по одному набору файлов, поэтому гидрация
сходится. Диагностика сохранена: одно предупреждение на путь, его пишет сама
точка поиска лоадера.

Вариант с `errorComponent` рассмотрен и отклонён. Ходовое утверждение, что под
`<Suspense>` Vue игнорирует `errorComponent`, **неверно** (проверено по
`@vue/runtime-core` 3.5.39: в suspensible-ветке он подставляется), но он всё
равно хуже: срабатывал бы и на ошибку исполнения импорта, не даёт передать
заглушке имя компонента и grid-стили, и attrs брика протекали бы в её корень.

Заодно выровнен ключ кеша: async-обёртка писалась по сырому пути, а читалась по
нормализованному — при пути с бэкслэшами запись не находилась и обёртка
пересоздавалась на каждую перерисовку.

**Сознательно не покрыто:** лоадер, который есть, но падает или не экспортирует
компонент. Это программная ошибка brick-компонента, а не деградация схемы;
подменять её той же заглушкой значило бы скрыть дефект. На неё нужен отдельный
error boundary со своей политикой.

**Проверка.** Prod-сборка (`.output`, запущенный из постороннего cwd) со
страницей, где рядом лежат настоящий brick-компонент и ссылка на удалённый:
200, компонент и его проп из схемы в сыром SSR-HTML, заглушка на месте
отсутствующего, в консоли браузера только целевое предупреждение — ошибок
гидрации нет. Контрольный прогон на версии до правки: 500 на всю страницу.
Два спека с мутационной проверкой.

**Файлы:** `src/runtime/modules/render/composables/useRendererBricks.ts`,
`test/render/rendererBricks.spec.ts`.

## 12. Потолок чтения сведён к одной константе, дедлайн получил запас

**Тип:** снятие дублирования + исправление политики дедлайна.

**Зачем.** Потолок чтения был объявлен дважды одним и тем же числом:
`PUBLIC_PAGE_REQUEST_TIMEOUT_MS` в клиенте published-страницы и
`BRICKS_API_READ_TIMEOUT_MS` в общих константах, откуда его берёт внешний дедлайн
вокруг того же вызова. Поднять клиентский потолок — и дедлайн начал бы обрезать
клиентский путь раньше транспорта, превращая реальную ошибку сервера в 504.

Отдельно middleware оставался единственным местом, где внешний дедлайн стоял
**без** `BRICKS_SSR_DEADLINE_MARGIN_MS`, хотя докстринг самой константы объявляет
запас обязательным.

**Что сделано.** Клиент published-страницы берёт общий потолок чтения; смысловая
оговорка про инертность потолка на SSR переехала на место применения. Внешний
дедлайн lookup'а вынесен в чистую утилиту `withPageLookupDeadline(operation,
isServer)`: на SSR — потолок чтения плюс запас, на клиенте дедлайна нет вовсе,
там живой сигнал ставит сам фетчер (проверено: и `publicPageFetcher`, и
`apiFetcher` применяют `applyApiRequestTimeout`).

**Зачем запас, если оба отказа дают 504.** Статус действительно один, но
совпадение границ отдаёт исход гонке: обработчик мог успеть вернуть собственную
ошибку с настоящим статусом и причиной, а generic `TimeoutError` внешнего
дедлайна её затирал. С запасом штатная ошибка доезжает первой, а дедлайн
остаётся аварийной стенкой на единственный случай, ради которого написан —
внутренний вызов Nitro не слушает `AbortSignal`. Плата: зависший SSR-lookup
завершается на 12-й секунде вместо 10-й. Если внешний SLO должен быть строго 10
секунд, складывать нельзя — тогда придётся снижать внутренний бюджет, а это
смена общей политики.

Заодно перестали врать сами константы: вводная файла называла их «потолками
запросов билдера», а комментарий чтения перечислял `usePublicPageClient` среди
клиентов с независимой копией того же числа — после правки он берёт эту
константу. Записано и почему два потолка остаются своими: бюджеты data sources и
внешнего backend'а настраиваются развёртыванием, то есть совпадают лишь по
дефолту.

**Что пиннят спеки.** Дедлайн: на потолке чтения ещё молчит, на потолке плюс
запас отклоняется, и отказ распознаётся как `TimeoutError` — то есть покраснеет и
на снятом запасе, и на выключенном дедлайне целиком. Клиент: бюджет каждого
запроса сверяется с общей константой через аргумент, с которым зовётся политика.
Проверять его по времени нельзя — ofetch свой таймер при выставленном сигнале не
ставит (`ofetch.CWycOUEr.mjs:261`), а живой потолок держит `AbortSignal.timeout`,
который фейковым таймерам vitest не подчиняется (проверено).

## 13. Границы контракта путей записаны в README

**Тип:** документация.

**Зачем.** Контракт «`brickPath` = путь относительно `srcDir`» верен для
playground, конвенциональных Nuxt 3 и 4 и рядового кастомного `srcDir`, но
молчал о том, где brick-файлы искаться не будут. Пользователь не мог отличить
неподдерживаемую раскладку от дефекта.

**Что сделано.** В разделе «Brick-компоненты» появился подраздел «Где
brick-файлы не ищутся»: переопределённый независимо от `srcDir` `vite.root`;
дополнительные каталоги компонентов (`components.dirs` и `addComponentsDir` из
Nuxt-модулей); каталоги из слоёв Nuxt; brick-файлы внутри пакетов npm; симлинки
за пределы Vite root. Формулировка — «не поддерживается и не гарантируется», а
не «не работает»: часть внешних симлинков сегодня проходит благодаря allow-list
workspace, но результат зависит от `realpath` и `preserveSymlinks`. Отдельно
сказано, что менять саму опцию `components` можно — ограничение только на
расположение brick-файлов, и обходится ре-экспортом из `<srcDir>/components`.

Инвариант коротко продублирован в коде — у паттерна скана и у карты лоадеров:
оба безусловно опирались на `vite.root === srcDir`, не говоря об этом.

**Проверено по факту:** в установленном `@nuxt/schema` 4.4.6 ключа `components`
в `dir` нет вовсе (`app`, `assets`, `layouts`, `middleware`, `modules`, `pages`,
`plugins`, `shared`, `public`), а верхнеуровневая опция объявлена как
`boolean | ComponentsOptions | ComponentsOptions['dirs']`. Модуль `vite.root` не
переопределяет — трогает только `optimizeDeps`.

**Автотеста нет сознательно:** проверка текста README не проверяет семантику, а
на планируемом сокращении набора такой спек — чистый груз.

**Файлы:** `README.md`, `src/bricks-manifest.ts`,
`src/runtime/modules/common/composables/useBrickImports.ts`.
