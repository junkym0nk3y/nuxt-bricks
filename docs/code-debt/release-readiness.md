# Готовность к публикации

Не долг кода, а условия, без которых пакет нельзя выложить или нельзя доверять его
гейту. Отдельный трек потому, что порядок здесь свой: первый пункт — внешние шаги
выкладки, которые не правятся кодом, остальные закрывают риски безопасности,
качества гейта и эксплуатации. Индекс — [README.md](README.md).

**Закрыл пункт — удали его из этого файла** и перенумеруй остальные: список
сокращается, а не помечается галочками. Отметка «сделано» превращает файл в
журнал, а журнал никто не перечитывает — история правки и так лежит в git.

## 1. Публикация ждёт публичного репозитория и первой ручной выкладки

**Где:** настройки репозитория на GitHub и страница пакета на npm. В самом
репозитории всё готово: `LICENSE` в корне и в `files`, верные
`repository`/`homepage`/`bugs`, `CHANGELOG.md`, `SECURITY.md`,
`.github/workflows/publish.yml` и ассерты лицензии и changelog в
`scripts/pack-smoke.mjs`.

Три условия не выполняются, и ни одно не правится кодом:

- **Репозиторий приватный.** Provenance выдаётся только публичному репозиторию с
  публичным пакетом, а ссылки из `package.json` ведут на страницу, которую
  посторонний не откроет.
- **Пакета `nuxt-bricks` в реестре нет** (`npm view nuxt-bricks` отвечает 404).
  Trusted publisher настраивается на странице **существующего** пакета, то есть
  первая публикация делается руками с интерактивной аутентификацией, и только после
  неё workflow'у есть против чего аутентифицироваться. Иначе первый прогон
  заканчивается `ENEEDAUTH`.
- **Private vulnerability reporting не включён.** Ссылка из `SECURITY.md` ведёт на
  форму, которая появляется только после включения в настройках Security.

Порядок: репозиторий становится публичным → одна ручная публикация `0.1.0` →
trusted publisher настраивается ровно на `junkym0nk3y/nuxt-bricks` и workflow
`publish.yml` → включается private vulnerability reporting. Дальше релизы идут
через workflow. После первой выкладки проверить `npm audit signatures` и что ссылки
на странице пакета ведут в репозиторий.

Пока публикация не в планах, пункт лежит здесь как список внешних шагов, а не как
работа по коду: запустить workflow нечем — он висит на ручном создании релиза, и
шаг публикации без trusted publisher падает.

## 2. Параметры scrypt ниже минимума OWASP

**Файлы:** `src/runtime/server/utils/auth/passwords.ts` (`SCRYPT_N = 16384`, `:13`),
литерал хеша в `migrations/0001_init.sql` и его копия в
`persistence/server/utils/defaultAdmin.ts`

Используется `N=2^14, r=8, p=1`. Рекомендация OWASP для scrypt начинается с
`N=2^17, r=8, p=1` либо эквивалентных trade-off конфигураций (`N=2^14` в них идёт с
`p=5`). Практический риск низкий: формат хеша самоописывающий
(`scrypt:N:r:p:salt:hash`), verify берёт параметры из самой строки, поэтому смена
дефолта не ломает существующие записи.

**Чинить — по шагам, каждый обязателен:**

- Бенчмарк на минимальном production-инстансе, выбрать baseline.
- `N=2^17` при `r=8` требует ≈134 МБ на одну деривацию (`128·N·r`), а дефолтный
  `maxmem` у node — 32 МБ: без явного `maxmem` в опциях `scrypt` вызов просто упадёт.
- Согласовать с bounded-семафором `scryptGate.ts`: `maxConcurrent = 4` при 134 МБ на
  деривацию даёт пик ≈536 МБ RSS только на логинах. Либо снижать одновременность,
  либо осознанно закладывать память.
- Перегенерировать `DUMMY_PASSWORD_HASH` с новыми параметрами. Иначе
  анти-enumeration ломается наоборот: ответ на несуществующий username станет заметно
  **быстрее** ответа на существующий.
- Rehash-on-login: после успешного verify, если параметры хеша ниже текущих, —
  перехешировать и обновить строку. В `IAuthAdapter` метода записи пароля нет
  (`getUserByUsername` только читает), значит расширяется интерфейс адаптера, а вместе
  с ним — `docs/external-backend-contract.md` и внешняя реализация.

Профит — соответствие рекомендации без принудительного сброса паролей: старые хеши
мигрируют молча при первом входе. Сложность средняя: кода немного, но правка расширяет
публичный контракт адаптера и меняет профиль памяти на пути логина, то есть требует
замера, а не только редактирования констант.

## 3. Вес редактора не под бюджетом

**Файлы:** `scripts/bundle-budget.mjs`,
`builder/shell/sidebar/utils/propertyEditorComponents.ts`

Бюджеты закрывают две поверхности — `entry` (потолок 122 KB gzip) и `published` (132).
Редактор не закрыт ничем, и наивное расширение скрипта третьей поверхностью проблему не
решит: замер по манифесту даёт для роута `builder/app/pages/builder.vue` ровно entry —
страница редактора это тонкая оболочка, всё содержимое приезжает через
`defineAsyncComponent`, поэтому такой «бюджет» был бы зелёным всегда и не мерил бы
ничего.

Фактический вес поддерева (`builder` + `text-editor` + `ui`) сверх entry — **571 KB
gzip в 54 чанках**, из них 309 KB (54%) — один ленивый вендорный чанк
`vanilla-jsoneditor` под редактор JSON-свойства
(`BuilderShellSidebarPropertyJsonEditor.vue`). Он же тянет `ajv` → `fast-uri` в
production dependency tree.

**Смешанные импорты** (компонент одновременно статический и динамический — code
splitting для него не работает) только размножились. Динамически они приезжают из
`propertyEditorComponents.ts` (`:11` checkbox, `:13` select, `:30` hex), а статически:

- `BricksHexInput.vue` — `BuilderShellSidebarPublishView.vue:30`;
- `BricksSelect.vue` — `BuilderShellSidebarPublishView.vue:31`,
  `TheBuilderUsersCreateModal.vue:48`, `BuilderMediaGalleryMetaPanel.vue:41`,
  `BuilderMediaGalleryUploadOptions.vue:44`;
- `BricksCheckbox.vue` — `BuilderCanvasItemContextMenu.vue:20`,
  `TheBuilderUsersCreateModal.vue:43`, `BuilderMediaGalleryUploadOptions.vue:42`.

**Чинить:** выбрать метрику, которая ловит рост — сумма чанков поддерева `builder/**`
либо реально переданный по сети JS после интерактива редактора (второе теперь дёшево,
e2e-инфраструктура уже есть). Добавить её поверхностью в `scripts/bundle-budget.mjs` и в
CI. Расшить смешанные импорты — либо статически импортировать эти три компонента везде,
либо динамически везде.

**Решение владельца про `vanilla-jsoneditor` принято: снимаем.** Замена — `prismjs`
(ядро плюс грамматика JSON) поверх `textarea`: прозрачное поле над подсвеченным
`<pre>` с синхронным скроллом, кнопка форматирования (`JSON.stringify(parsed, null, 2)`)
и ошибка разбора под полем. Замер сборкой (esbuild, minify + gzip): **3.7 KB gzip
против 309** — то есть уходит не половина веса поддерева, а 305 KB из 571. Вместе с
библиотекой из production dependency tree уходят `ajv`, `jmespath`, `json-source-map`
и `natural-compare-lite`.

Что теряется и принято потерянным: парные скобки, автоотступ и undo самого редактора
(браузерный undo в `textarea` остаётся). Кнопка форматирования закрывает отступы
надёжнее автоотступа, а для скринридера обычный `textarea` лучше, чем CodeMirror.
Промежуточный вариант — собрать CodeMirror 6 вручную, 98.5 KB gzip, полностью
сохранив нынешнюю эргономику — отклонён: 98.5 KB ради одного редактора свойства.

Радиус: сам SFC `BuilderShellSidebarPropertyJsonEditor.vue`, удаление
`json-editor-vue` и `vanilla-jsoneditor` из `package.json`, чистка их и обслуживающих
пакетов из optimize-списка в `src/module.ts` и builder-only regex в
`src/module-setup.ts`, спеки на валидный и невалидный JSON, внешний сброс значения и
оба типа свойства (`object`, непримитивный `array`). Редактор есть в макете —
обновляется и он (правило `docs/figma-sync-workflow.md`).

Сейчас в редактор можно добавить мегабайт, и ни одна проверка не заметит.

## 4. Deprecated транзитивные зависимости

Свежая установка у потребителя печатает deprecation-предупреждения: `vue-i18n@10.0.8`
(вложен под `@intlify/vue-i18n-extensions@8` внутри `@nuxtjs/i18n@10.6.0`; верхний
уровень уже на 11.4.9), `unplugin-vue-router@0.19.2` (транзитив `nuxt@3.21.x`),
`glob@10.5.0` (через `archiver` у `nitropack`).

Известных уязвимостей в них нет — это шум, но шум в первом впечатлении от пакета.

**Чинить:** поднимать верхнеуровневые пакеты, которые их держат. Обновление
`@nuxtjs/i18n` до 10.6.0 убрало уязвимый `js-yaml`, но не deprecated
`vue-i18n@10.0.8`: его всё ещё держит актуальный `@intlify/vue-i18n-extensions@8`.
`unplugin-vue-router` и `glob` приходят из Nuxt и Nitro. Для всех трёх остаётся ждать
апстрим либо взвешивать `overrides`, что рискованнее самих предупреждений.

Сложность низкая по действиям, но результат не в нашей власти: все три цепочки
чинятся только апстримом.
