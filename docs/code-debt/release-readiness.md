# Готовность к публикации

Не долг кода, а условия, без которых пакет нельзя выложить или нельзя доверять его
гейту. Отдельный трек потому, что порядок здесь свой: первые два пункта — блокеры
публикации, остальные три делают проверки способными ловить регрессии. Индекс —
[README.md](README.md).

---

## 1. Блокирующий CI-job `npm audit` красный: 11 уязвимостей в prod-зависимостях

**Файл:** `.github/workflows/ci.yml` (job `audit`, `:139-150`)

Job запускает `npm audit --omit=dev` блокирующе. Планка пробита и продолжает падать:
было 8 уязвимостей, сейчас **11** — 8 high, 2 moderate, 1 low (сверено прогоном).
Значит любой push в `main` или PR валится на этом job, и пока он красный, гейт
перестаёт различать «чисто» и «появилось новое».

Не все они теоретические. `sharp` — прямая зависимость, обрабатывает **загруженные
пользователем** изображения; CVE в libvips приходят ровно на этот путь. `linkify-it`
(quadratic DoS на `mailto`-сканере) приезжает с `markdown-it`, которым рендерится
документация билдера.

| Пакет               | Severity | Откуда                                                                        |
| ------------------- | -------- | ----------------------------------------------------------------------------- |
| `sharp@0.34.5`      | high     | прямая зависимость                                                            |
| `postcss`           | high     | `@vue/compiler-sfc`, `vite` (через `@intlify/unplugin-vue-i18n`)              |
| `nanoid`            | high     | `postcss`, та же цепочка                                                      |
| `linkify-it@5.0.1`  | high     | `markdown-it@14.2.0`                                                          |
| `js-yaml`           | high     | `@nuxtjs/i18n@10.4.0` → `@rollup/plugin-yaml`                                 |
| `fast-uri`          | high     | `vanilla-jsoneditor` → `ajv`                                                  |
| `brace-expansion`   | high     | `@kalimahapps/vue-icons` → `@typescript-eslint/parser` → `minimatch`          |
| `ip-address`        | high     | `@kalimahapps/vue-icons` → `@modelcontextprotocol/sdk` → `express-rate-limit` |
| `hono`              | moderate | `@kalimahapps/vue-icons` → `@modelcontextprotocol/sdk`                        |
| `@hono/node-server` | moderate | то же                                                                         |
| `body-parser`       | low      | то же → `express`                                                             |

**Чинить.** Десять из одиннадцати `npm audit` объявляет исправимыми в пределах semver
(`fixAvailable: true`) — обновлением lock-файла, без правок кода; на origin уже лежат
ветки dependabot, включая объединённую `minor-and-patch`. `sharp` требует мажора
`0.34.5 → 0.35.3`: смотреть changelog по API обработки изображений, прогонять
`smoke:integration` (там MinIO и реальная загрузка) и проверять сборку под нативные
бинарники.

**Отдельным решением — пять уязвимостей из одиннадцати приходят одной цепочкой**
`@kalimahapps/vue-icons` → `@modelcontextprotocol/sdk` / `@typescript-eslint/parser`:
пакет иконок тащит в prod-дерево потребителя MCP SDK, express и парсер TypeScript.
Стоит ли этот набор иконок такого хвоста — вопрос не к обновлению лока.

Сложность низкая для десяти пунктов, средняя для `sharp` — мажор на нативной
библиотеке, нужен интеграционный smoke, а не только unit-тесты.

## 2. npm-пакет не готов юридически и операционно

**Файлы:** `package.json`, корень репозитория

`package.json` объявляет `"license": "MIT"`, но файла `LICENSE` нет ни в корне, ни в
`files` (там только `dist`, `migrations`, `docs/external-backend-contract.md`), то есть
и в tarball. Поле `repository` указывает `saintfr3ak/nuxt-bricks`, а `git remote` —
`junkym0nk3y/nuxt-bricks`: у публикации будет ссылка не туда. Нет `CHANGELOG.md`,
`SECURITY.md`, `CONTRIBUTING.md` и release workflow — сообщить об уязвимости и понять,
что изменилось между версиями, некуда и нечем. (Проверено: ни одного из четырёх файлов
в корне нет.)

**Чинить:** подтвердить правообладателя и лицензию, положить `LICENSE` в корень и в
`files`, исправить `repository`/`homepage`/`bugs`, завести changelog и контакт для
security, собрать release workflow с provenance, повторно прогнать
`npm run smoke:pack`.

Это единственный блокер публикации, который нельзя обойти кодом. Сложность низкая по
объёму работ, но упирается в **решение владельца**: кто правообладатель, под какой
лицензией и какой репозиторий считать публичным.

## 3. Параметры scrypt ниже минимума OWASP

**Файлы:** `src/runtime/server/utils/auth/passwords.ts` (`SCRYPT_N = 16384`, `:13`),
литерал хеша в `migrations/0001_init.sql` и его копия в
`persistence/server/utils/defaultAdmin.ts`

Используется `N=2^14, r=8, p=1`. Рекомендация OWASP для scrypt начинается с
`N=2^17, r=8, p=1` либо эквивалентных trade-off конфигураций (`N=2^14` в них идёт с
`p=5`). Практический риск низкий: формат хеша самоописывающий
(`scrypt:N:r:p:salt:hash`), verify берёт параметры из самой строки, поэтому смена
дефолта не ломает существующие записи.

**Чинить — по шагам, каждый обязателен:**

- Бенчмарк на минимальном production-инстансе, выбрать baseline.
- `N=2^17` при `r=8` требует ≈134 МБ на одну деривацию (`128·N·r`), а дефолтный
  `maxmem` у node — 32 МБ: без явного `maxmem` в опциях `scrypt` вызов просто упадёт.
- Согласовать с bounded-семафором `scryptGate.ts`: `maxConcurrent = 4` при 134 МБ на
  деривацию даёт пик ≈536 МБ RSS только на логинах. Либо снижать одновременность,
  либо осознанно закладывать память.
- Перегенерировать `DUMMY_PASSWORD_HASH` с новыми параметрами. Иначе
  анти-enumeration ломается наоборот: ответ на несуществующий username станет заметно
  **быстрее** ответа на существующий.
- Rehash-on-login: после успешного verify, если параметры хеша ниже текущих, —
  перехешировать и обновить строку. В `IAuthAdapter` метода записи пароля нет
  (`getUserByUsername` только читает), значит расширяется интерфейс адаптера, а вместе
  с ним — `docs/external-backend-contract.md` и внешняя реализация.

Профит — соответствие рекомендации без принудительного сброса паролей: старые хеши
мигрируют молча при первом входе. Сложность средняя: кода немного, но правка расширяет
публичный контракт адаптера и меняет профиль памяти на пути логина, то есть требует
замера, а не только редактирования констант.

## 4. Хвосты релизного гейта: axe, пороги покрытия, непокрытые сценарии

**Файлы:** `e2e/specs/`, `vitest.config.ts`, `.github/workflows/ci.yml`

Браузерный гейт есть — job «Critical browser flows», восемь сценариев в
`builder-critical-flows.spec.ts` (5) и `tab-bar-keyboard.spec.ts` (3). Из заявленного
полного lifecycle не покрыто: вход (фикстура поднята на `auth.mode: 'basic'`,
`e2e/fixture/nuxt.config.ts:8-10`, шага логина в спеках нет), импорт, публикация из
UI, конфликт версий и восстановление после него.

Axe-проверок нет вовсе (ни зависимости, ни вызова), то есть регрессия доступности
проходит молча. Порогов покрытия тоже нет: в `vitest.config.ts` секции `coverage` не
существует, `@vitest/coverage-v8` не установлен.

**Чинить:** дописать недостающие сценарии; подключить `@axe-core/playwright` на
двух-трёх ключевых экранах; включить coverage v8 с порогами по каталогам, а не
глобально.

**Оговорка по очерёдности, важнее самой работы.** Сценарий конфликта версий требует
управляемой гонки — образец уже написан в спеке про опоздавший save, так что это работа
по образцу. А вот **пороги покрытия ставить до сокращения тестового набора нельзя**:
набор признан избыточным (216 спеков) и планируется срез порядка 90%, пороги
зафиксируют ровно то, что собираются вырезать (см. «`test/README.md` отстал от состава
спеков» в [решениях владельца](owner-decisions.md)).

Предпосылка для axe: пока редактор галереи в сайдбаре недоступен с клавиатуры
(см. [П2](p2-defects.md)), a11y-проверки включать нечего — они сразу покраснеют на
известном.

## 5. Вес редактора не под бюджетом

**Файлы:** `scripts/bundle-budget.mjs`,
`builder/shell/sidebar/utils/propertyEditorComponents.ts`

Бюджеты закрывают две поверхности — `entry` (потолок 122 KB gzip) и `published` (132).
Редактор не закрыт ничем, и наивное расширение скрипта третьей поверхностью проблему не
решит: замер по манифесту даёт для роута `builder/app/pages/builder.vue` ровно entry —
страница редактора это тонкая оболочка, всё содержимое приезжает через
`defineAsyncComponent`, поэтому такой «бюджет» был бы зелёным всегда и не мерил бы
ничего.

Фактический вес поддерева (`builder` + `text-editor` + `ui`) сверх entry — **571 KB
gzip в 54 чанках**, из них 309 KB (54%) — один ленивый вендорный чанк
`vanilla-jsoneditor` под редактор JSON-свойства
(`BuilderShellSidebarPropertyJsonEditor.vue`). Он же тянет `ajv` → `fast-uri` из
пункта 1.

**Смешанные импорты** (компонент одновременно статический и динамический — code
splitting для него не работает) только размножились. Динамически они приезжают из
`propertyEditorComponents.ts` (`:11` checkbox, `:13` select, `:30` hex), а статически:

- `BricksHexInput.vue` — `BuilderShellSidebarPublishView.vue:30`;
- `BricksSelect.vue` — `BuilderShellSidebarPublishView.vue:31`,
  `TheBuilderUsersCreateModal.vue:48`, `BuilderMediaGalleryMetaPanel.vue:41`,
  `BuilderMediaGalleryUploadOptions.vue:44`;
- `BricksCheckbox.vue` — `BuilderCanvasItemContextMenu.vue:20`,
  `TheBuilderUsersCreateModal.vue:43`, `BuilderMediaGalleryUploadOptions.vue:42`.

**Чинить:** выбрать метрику, которая ловит рост — сумма чанков поддерева `builder/**`
либо реально переданный по сети JS после интерактива редактора (второе теперь дёшево,
e2e-инфраструктура уже есть). Добавить её поверхностью в `scripts/bundle-budget.mjs` и в
CI. Расшить смешанные импорты — либо статически импортировать эти три компонента везде,
либо динамически везде.

**Отдельным решением — нужен ли `vanilla-jsoneditor` вообще:** 309 KB gzip ради
редактора JSON-свойства. Отказ одним движением снимает половину веса поддерева и одну
уязвимость из пункта 1.

Сейчас в редактор можно добавить мегабайт, и ни одна проверка не заметит.

## 6. Deprecated транзитивные зависимости

Свежая установка у потребителя печатает deprecation-предупреждения: `vue-i18n@10.0.8`
(вложен под `@intlify/vue-i18n-extensions@8` внутри `@nuxtjs/i18n@10.4.0`; верхний
уровень уже на 11.4.6), `unplugin-vue-router@0.19.2` (транзитив `nuxt@3.21.x`),
`glob@10.5.0` (через `archiver` у `nitropack`).

Известных уязвимостей в них нет — это шум, но шум в первом впечатлении от пакета.

**Чинить:** поднимать верхнеуровневые пакеты, которые их держат. `@nuxtjs/i18n` всё
ещё на 10.4.0, хотя вышел 10.6.0 — и он же тащит уязвимый `js-yaml` из пункта 1, так
что обновление закрывает оба. `unplugin-vue-router` и `glob` приходят из Nuxt и Nitro —
тут только ждать апстрим либо взвешивать `overrides`, что рискованнее самих
предупреждений.

Сложность низкая по действиям, но результат не в нашей власти: две из трёх цепочек
чинятся только апстримом.
