# П2 — дефекты и края поведения

Дефект есть, но радиус ограничен: неверная подпись вместо неработающей команды,
недостижимая из интерфейса опция, край, который держится соседней проверкой.
Индекс и правила чтения — [README.md](README.md).

**Закрыл пункт — удали его из этого файла** и перенумеруй остальные: список
сокращается, а не помечается галочками. Отметка «сделано» превращает файл в
журнал, а журнал никто не перечитывает — история правки и так лежит в git.

## 1. Осиротевшие объекты хранилища некому убрать

**Файлы:** `persistence/server/utils/mediaOrchestration.ts` (`deleteVariantFiles`,
`registerUploadedMedia`), `persistence/server/s3/s3ObjectCleanup.ts`
(`discardUnconfirmedObject`), `persistence/server/s3/s3PublishAdapter.ts` (`listFiles`)

Сироты в бакете появляются штатно, и это следствие принятого приоритета: строка БД,
указывающая на удалённый файл, ломает галерею и опубликованные страницы, а объект без
строки — невидимый мусор, поэтому при **неизвестном** исходе записи файлы сознательно
сохраняются. Мест таких несколько: неизвестный исход `createMedia` (запись могла
закоммититься), отказ самой best-effort уборки — и удаление вариантов, которое не
блокирует удаление файла и может не дойти.

Каждое из них логируется адресом объекта, но фонового сборщика нет: уборка держится на
том, что кто-то прочитает лог. Обратное направление (бакет → БД) в коде есть —
`mediaImport.ts`, — а сверки в сторону уборки нет ни скриптом, ни ручкой. То есть
решение «при неизвестном исходе оставляем файл» односторонее: у него нет второй
половины.

**Чинить:** проход по префиксу медиа (`listFiles` у publish-адаптера уже пагинирует) с
вычитанием адресов, встречающихся в `bricks_media` (`url`, `preview_url`, `mock_url`).
Обязательны две страховки: **порог возраста объекта**, иначе сборщик снесёт файл,
который прямо сейчас грузится и ещё не зарегистрирован (окно между PUT и INSERT), и
**dry-run по умолчанию**. Вариант проще — не сборщик, а отчёт: тот же diff без
удаления, решение по списку принимает человек.

Превью страниц сюда не входят: у них своя уборка по префиксу страницы
(`prunePageThumbnailsAfterUpload`, `pageThumbnails.ts:140`). Незавершённые multipart-
заливки — тоже не сюда: это не объекты, `listFiles` их не видит, и закрываются они
lifecycle-правилом бакета `AbortIncompleteMultipartUpload` (см. раздел Production в
`README.md`).

**Решение владельца: отдельная команда, запускаемая руками** — на пожарный случай, а
не фоновый сборщик и не durable outbox в транзакции. То есть CLI рядом с
`bricks-migrate`: dry-run по умолчанию, удаление отдельным флагом, порог возраста
объекта обязателен. Расписания у неё нет намеренно: неубранный объект — невидимый
мусор, и цена ежедневного прохода по бакету выше цены этого мусора.

Одним заходом закрываются два префикса, а не один: медиа (сверка с `bricks_media` —
`url`, `preview_url`, `mock_url`) и аватары (сверка с `bricks_users.avatar_url`).
Аватары попадают сюда потому, что у них второй попытки нет вообще: URL прежнего файла
после замены нигде не хранится, а после удаления учётки исчезает и строка, то есть
любой временный отказ хранилища оставляет объект навсегда.

Сложность: низкая для отчёта, средняя для удаляющего прохода — цена ошибки удалённый
файл живой записи, поэтому нужен прогон на реальном бакете.
